# R12 학습 노트 — 잠자던 오디오 인프라 깨우기 & 게임필 2차

> 2026-06-11. R12 "게임필 2차 + 오디오·아이덴티티" 합격(9.0/10, 1회차).
> 백로그 6항목 + R11 이관 가드 + 사용자 추가 3건(BGM·효과음·앱 이름)을 한 Phase로.

---

## 1. BGM — 새로 만든 게 아니라 "스위치를 켠" 것

### 이중 비활성이라는 상태

BGM 재생기는 옛날 Phase 6에서 이미 완성돼 있었습니다 — 페이드 인/아웃, 전화 오면
멈췄다 복귀, 백그라운드 처리, 긴장 구간에서 빨라지는 rate 1.15까지 전부요. 그런데
**두 개의 자물쇠**가 잠겨 있었습니다:

1. `isBGMEnabled` 플래그가 꺼져 있음
2. 재생할 음원 파일(bgm.m4a)이 번들에 아예 없음

코드는 "음원이 없으면 조용히 아무것도 안 함(noop)"으로 설계돼 있어서, 그동안 게임이
조용했던 건 버그가 아니라 **재료가 안 들어온 것**이었습니다.

Spring 비유: `@ConditionalOnProperty`(플래그)와 `@ConditionalOnResource`(파일)가
**둘 다** 걸린 Bean입니다. 설정도 켜야 하고 리소스도 클래스패스에 있어야 빈이 뜨죠.
이번 작업은 프로퍼티 한 줄 + 리소스 파일 하나를 넣어 잠자던 빈을 깨운 겁니다.

### 음원은 스크립트로 — 그리고 "드롭인 계약"

음원은 파이썬 스크립트(tools/generate_bgm.py)로 합성했습니다 — 8마디 124BPM 칩튠
루프, 외부 라이브러리 0, 난수 0(돌릴 때마다 같은 결과 = 재현 가능). 중요한 건
**코드 어디에도 이 곡의 BPM이나 길이에 의존하는 부분이 없다**는 점입니다. 즉
`bgm.m4a` 파일만 바꿔 끼우면 다른 곡이 그대로 적용됩니다.

이 게임의 정체성이 "간호 실습 중에 작곡한 자전적 경험"이니까, 지금 곡은
**자리만 잡아두는 플레이스홀더**고, 진짜 자작곡으로 교체하는 게 완성형입니다.

## 2. 효과음 4종 — "미리 굽기" 규칙 지키기

스킬 발동·목표 달성 팡파레·니어미스·졸업 스팅어 4종을 추가했는데, 전부 앱 시작
시점에 **미리 렌더링**해 둡니다. 게임 도중(매 프레임 60번 도는 길)에 소리를
합성하면 버벅임의 원인이 되니까요.

Spring 비유: 요청 처리 중에 무거운 객체를 만들지 않고, 기동 시점에
`@PostConstruct`로 캐시를 예열해 두는 패턴입니다. 검수자는 "렌더 함수를 부르는
곳이 예열 함수 단 한 곳뿐"임을 grep으로 확인했습니다 — 규칙이 지켜졌다는 증명을
호출처 개수로 하는 거죠.

## 3. 문서가 틀리고 코드가 맞았던 사례

백로그에는 "수간호사 순찰 루트가 난이도별로 좌표가 동일하다"고 적혀 있었는데,
planner가 코드를 직접 열어보니 **이미 난이도별로 달랐습니다**(easy 왕복 /
normal X자 / hard 사각). 문서를 믿고 "루트 분화"를 구현했다면 이미 있는 걸 다시
만들 뻔했죠. 그래서 설계를 "루트 재설계"에서 **"12초마다 순찰 방향 반전"**으로
바꿨습니다 — 더 작은 변경으로 같은 목적(예측 불가능성)을 달성합니다.

반전에도 디테일이 있습니다: 길 한가운데서 휙 돌면 부자연스러우니까 **모퉁이
(waypoint)에 도착하는 순간에만** 방향을 바꿉니다. 유저 눈에는 "원래 그런 순찰"로
보이게요.

> 이 프로젝트의 철칙 재확인: **설계서와 코드가 다르면 코드가 진실**. 문서는 쓰는
> 순간부터 낡기 시작합니다.

## 4. 앱 이름 — 한 줄이지만 "불변 조건 해석"을 남긴 한 줄

홈 화면 이름을 "김간호는 음악박사"로 바꾸는 건 Info.plist에 `CFBundleDisplayName`
키 하나 추가입니다. 그런데 이 프로젝트엔 "Info.plist 권한 불변"이라는 불변 조건이
있어서, 그냥 바꾸면 위반처럼 보일 수 있었죠. SPEC에 **"이 조항은 권한(permission)
항목 한정이고, 표시명은 권한이 아니다"라는 해석을 명문으로 남기고** 진행했습니다.

규칙과 변경이 충돌해 보일 때는 몰래 지나가지 말고, 해석을 문서로 남기는 것 —
나중에 "이거 왜 바꿨지?"의 답이 됩니다.

## 5. 정직한 미검증 표기 — "못 본 것"을 숨기지 않기

수간호사 반전(12초 후 발동)은 시뮬레이터 자동 주행이 12초를 못 버티고 죽어서
generator 6회, evaluator 2회 모두 라이브로 못 봤습니다. 두 에이전트가 **독립적으로
같은 한계를 재현**했고, 산술이 결정적이고 디버그 로그 장치가 있으니 위험은 낮다고
판정 — 대신 "실기기에서 16초 이상 1판" 체크리스트로 넘겼습니다.

테스트로 치면: 통합 테스트가 환경 한계로 못 도는 케이스를 `@Disabled("사유")`로
남기되, 사유와 수동 검증 절차를 명시하는 것. 조용히 빼는 것과는 다릅니다.

## 오늘의 교훈

1. **"없다"고 보이는 기능도 먼저 창고를 봐라.** BGM은 0부터 만들 일이 아니라
   재료 2개(플래그+파일)를 넣을 일이었다.
2. **교체 가능성을 계약으로 남겨라.** 음원의 BPM/길이에 코드가 의존하지 않게 해서
   "파일만 바꾸면 끝"을 보장했다 — 자작곡 교체가 1분 작업이 됐다.
3. **문서-코드 충돌 시 코드가 진실, 그리고 발견은 기록.** 오기 하나가 설계를 더
   작고 정확한 변경으로 바꿨다.
4. **규칙 해석은 명문으로.** 표시명 변경이 "Info.plist 불변"과 충돌해 보일 때,
   해석을 SPEC에 남기고 갔다.
