## 2. 가장 중요했던 것 — Firestore "출입 규칙"

### 무슨 일이 있었나?

우리 게임은 점수를 **인터넷 저장소(Firebase)** 에 올려요. 코드를 보면 이렇게 저장해요:

```
users / 내아이디 / scores / ...   ← "users 방"에 내 점수를 둠
```

그런데 이 저장소에는 **"누가 어느 방에 들어올 수 있는지" 정하는 규칙**이 따로 있어야 해요.
이게 없으면 저장소는 보통 **"테스트 모드 = 아무나 다 들어와도 됨"** 으로 열려 있어요.

> 🏫 **Spring 비유**: Spring Security의 `@PreAuthorize("#uid == authentication.name")` 와 똑같아요.
> 이 어노테이션을 안 붙이면, 남의 ID 데이터를 막 가져오는 API가 그냥 열려버리죠.
> Firestore 규칙 = **서버 쪽 접근 권한 설정** 그 자체예요.

### 더 황당했던 점

저장소 규칙 파일이 **딴 데(작업 폴더 구석)에 하나 굴러다니고 있었는데**, 그 규칙은 엉뚱한 방 이름(`profiles`, `leaderboard`)을 지키고 있었어요. 정작 코드가 쓰는 방은 `users`인데요!

- 만약 그 엉뚱한 규칙을 그대로 적용했다면 → 코드가 `users` 방에 못 들어가서 **점수 저장이 전부 실패**.
- 규칙을 아예 안 넣었다면 → **아무나 다 들어오는** 보안 구멍.

> 🍔 **쉬운 비유**: 우리 집 현관문(`users`)엔 자물쇠가 없는데, 엉뚱하게 옆집 창고(`profiles`)에만 자물쇠를 달아둔 상황. 도둑 입장에선 우리 집이 활짝 열린 거죠.

### 어떻게 고쳤나

코드가 실제로 쓰는 방(`users/내아이디` 와 그 아래 `scores`, `progress`)에 딱 맞춰서
**"본인만 자기 방을 읽고/쓰고/지울 수 있다"** 는 규칙을 새로 써서 `firebase/firestore.rules` 에 저장했어요.

```
function isOwner(uid) {
  return request.auth != null && request.auth.uid == uid;  // 로그인했고 + 그게 본인이면
}
match /users/{uid} {
  allow read, create, update, delete: if isOwner(uid);     // 본인만 허용
}
```

⚠️ **단, 이 파일은 "써둔 것"일 뿐, 아직 "적용"은 안 됐어요.** 형규님이 한 줄 실행해야 진짜 잠깁니다:

```bash
firebase deploy --only firestore:rules
```

> 🏫 **Spring 비유**: 코드에 `@PreAuthorize`를 적어둔 것 ≠ 서버 배포. 배포(`deploy`)를 해야 운영에 반영되는 것과 똑같아요.

## 3. `.gitignore` — 안 올려도 되는 물건 골라내기

깃(Git)은 "어떤 파일을 기록할지" 정하는 `.gitignore` 라는 목록이 있어요. 그런데 이게 **텅 비어 있었어요.**
그래서 이런 것들이 깃에 같이 올라가 있었죠:

- `.DS_Store` — 맥이 폴더마다 자동으로 만드는 **쓰레기 파일**
- `xcuserstate` — Xcode가 "내가 어느 파일 열어놨는지" 기억하는 **나만의 임시 메모**
- `.claude/worktrees/` — 작업용 임시 폴더

> 🏫 **Spring 비유**: 자바 프로젝트에서 `target/` 폴더(빌드 결과물)나 `.idea/`(IntelliJ 설정)를 깃에 안 올리잖아요? 똑같아요. **결과물·개인 설정은 깃에 안 넣는 게 원칙**이에요.

고친 방법:
1. `.gitignore` 파일을 새로 만들어 위 항목들을 적음 (앞으로는 자동으로 안 올라감)
2. 이미 올라가 있던 건 `git rm --cached` 로 **추적만 해제** (실제 파일은 안 지움 — 그냥 "깃아, 이건 이제 신경 쓰지 마" 하는 것)

## 4. 성능 — 똑같은 걸 매번 새로 그리지 말자

### 4-1. 적 캐릭터 그림 "재사용" (캐싱)

적 캐릭터(수간호사·석조무사·이교수)는 방향이 바뀔 때마다 그림을 **새로 그리고 있었어요.**
왼쪽 볼 때 그리고, 또 왼쪽 보면 또 그리고... 똑같은 그림인데도요.

반면 **주인공(PlayerNode)은 이미 영리하게** "한 번 그린 그림을 서랍에 넣어두고 재사용" 하고 있었어요.
그래서 적들도 주인공과 **똑같은 방식**으로 바꿨어요.

```swift
// 서랍(캐시)을 먼저 열어봄 → 있으면 그거 쓰고, 없을 때만 새로 그림
if let cached = textureCache[direction]?[frame] { return cached }
let texture = PixelSpriteRenderer.texture(...)   // 처음 한 번만 그림
textureCache[direction]?[frame] = texture        // 서랍에 넣어둠
```

> 🥮 **쉬운 비유**: 붕어빵을 주문마다 반죽부터 새로 하는 게 아니라, **붕어빵 틀로 찍어내서** 재사용하는 거예요. 방향 4개 × 동작 3개 = 최대 12개만 그려놓으면 게임 끝까지 그것만 돌려쓰면 돼요.

> 🏫 **Spring 비유**: `@Cacheable` 어노테이션과 똑같아요. 같은 입력이면 메서드를 다시 실행하지 않고 저장해둔 결과를 바로 돌려주죠.

### 4-2. 점수판 "안 바뀌면 다시 안 그림"

화면 위 점수판(HUD)은 1초에 60번 갱신돼요. 그런데 점수가 `100` 그대로인데도 **매번 "100"이라고 다시 쓰고** 있었어요.

그래서 **"직전에 뭘 보여줬는지 기억"** 해뒀다가, 값이 진짜 바뀌었을 때만 다시 쓰게 했어요.

```swift
if score != lastDisplayedScore {   // 점수가 진짜 바뀌었을 때만
    lastDisplayedScore = score
    scoreSlot.setValue("\(score)")
}
```

> 📋 **쉬운 비유**: 칠판에 "100점"이라고 써 있는데, 1초에 60번씩 지웠다 똑같이 다시 쓰는 건 헛수고잖아요. 점수가 바뀔 때만 고쳐 쓰면 되죠.

#### 여기서 조심했던 함정 🕳️
"기억해뒀다 같으면 건너뛰기"를 잘못하면 **첫 화면이 안 그려지는 버그**가 생겨요.
처음 점수가 `0`인데, 기억값도 `0`으로 시작하면 "어, 안 바뀌었네?" 하고 건너뛰어서 **빈 칸**이 되거든요.

그래서 기억값을 숫자가 아니라 **"아직 아무것도 안 보여줬음"(`nil`)** 으로 시작하게 했어요.
처음 한 번은 무조건 그리고, 그 다음부터 비교하는 거죠.

> 🏫 **Spring 비유**: 자바의 `Integer`(null 가능) vs `int`(0이 기본값) 차이예요. `int score = 0` 으로 두면 "안 들어온 0"과 "진짜 0"을 구분 못 하죠. 그래서 `Integer`(= Swift의 `Int?`)로 둬서 **null(=아직 없음)** 을 따로 표현한 거예요.

## 5. 점검하면서 배운 자세

- **"문제 같다"는 보고를 그대로 믿지 않기.** 자동 점검 도구가 "적 그림을 매 프레임 새로 그린다(심각)!"고 했지만, 직접 코드를 열어보니 **방향이 바뀔 때만** 그리고 있었어요. 거짓 경보였죠. → 항상 **내 눈으로 코드를 확인**하고 판단해야 해요.
- **확실한 것과 애매한 것을 나누기.** 보안 구멍처럼 확실한 건 바로 고치고, 성능처럼 "동작이 바뀔 위험"이 있는 건 **검증 파이프라인(Planner→Generator→Evaluator)** 을 거쳐 안전하게 고쳤어요.
- **"고쳤는데 똑같이 보여야 한다"는 게 제일 어렵다.** 이번 성능 작업의 핵심 목표는 *플레이어가 아무 차이도 못 느끼는 것*. 눈에 보이는 결과는 0% 바뀌고, 속만 효율적으로 바꾸는 게 진짜 실력이에요.
