# R1 학습 노트 — 엔진 코어 (게임은 그대로, 심장만 교체)

> 그랜드 리팩토링 v3의 두 번째 단계. R0가 "서랍 정리"였다면 R1은 **달리는 차의 엔진을 멈추지 않고 갈아 끼운** 작업입니다. 플레이어가 "뭔가 달라졌는데?"라고 느끼면 실패인 단계였어요.

## 오늘 한 일 한 줄 요약

매 프레임(초당 60번) 화면 전체를 뒤지던 코드를 "명단 관리"로 바꾸고, 쓰고 버리던 노드들을 재사용하게 하고, 바닥 타일 640개를 1개로 합쳤습니다. 게임 동작은 그대로, 화면에 떠 있는 노드 수는 1,491개 → 269개.

## 1. EntityRegistry — 전교생 수색을 명단 확인으로

**전**: "지금 화면에 F 학점 폭탄이 몇 개 날아다니지?"를 알아내려고 게임이 **매 프레임** 화면의 모든 노드에게 "너 이름이 projectile이니?"라고 물었습니다(`enumerateChildNodes`). 초당 60번, 전교생을 한 명씩 붙잡고 "너 3반이니?"라고 묻는 셈이에요.

**후**: `EntityRegistry`라는 명단을 만들었습니다. 폭탄이 태어날 때 명단에 적고(register), 사라질 때 지웁니다(unregister). "몇 개야?"는 이제 명단의 길이만 보면 끝 — 수색이 사라졌습니다.

**Spring으로 치면**: 매 요청마다 `SELECT * FROM users WHERE role='...'`로 풀스캔하던 것을, 변경 시점에만 갱신되는 인메모리 캐시(또는 일급 컬렉션)로 바꾼 것입니다. "조회가 잦고 변경이 드물면 조회 시점이 아니라 변경 시점에 일하라"는 그 원칙이에요.

## 2. ObjectPool — 종이컵에서 머그컵으로

**전**: 음표·폭탄·청진기·점수 팝업은 태어나서(생성) 몇 초 살다가 버려졌습니다(파괴). 45초 게임 동안 수백 번. 손님 올 때마다 종이컵을 새로 뜯고 버리는 카페죠. 생성/파괴는 비싸고, 그 비용이 쌓이면 프레임이 출렁입니다.

**후**: `ObjectPool` — 머그컵 선반입니다. 쓰고 나면 버리지 않고 **씻어서(reset) 선반에 돌려놓고**, 다음 손님에게 다시 내줍니다. 게임 시작 때 미리 채워두는 것(예열: 폭탄 12·음표 16·청진기 6·팝업 8)까지 합니다.

**Spring으로 치면**: 이건 정확히 **DB 커넥션 풀(HikariCP)** 입니다.

| 게임 | HikariCP |
|---|---|
| `obtain()` | `getConnection()` |
| `recycle()` | `close()` — 실제로 안 닫고 풀에 반납 |
| `resetForReuse()` | 커넥션 상태 초기화 (autoCommit 원복 등) |
| 예열 12개 | `minimumIdle` |

**씻기(reset)가 제일 어렵습니다.** 이전 사용자의 흔적 — 남은 액션(타이머), 투명도, 크기, 속도, "매혹됨" 상태 — 을 하나라도 빠뜨리면, 다음 손님이 이전 손님의 립스틱 자국이 묻은 컵을 받게 돼요. 실제로 체크리스트를 만들어 전수 점검했습니다. 커넥션 풀에서 트랜잭션 상태를 안 치우고 반납하면 다음 요청이 터지는 것과 같은 사고입니다.

**이중 회수 가드**도 필수였어요. 폭탄이 "벽에 맞음"과 "수명 만료"로 동시에 반납 요청될 수 있거든요. 같은 컵을 선반에 두 번 꽂으면 두 손님이 같은 컵을 받는 대참사 — 이미 선반에 있으면 무시하도록 막았습니다(멱등성, idempotent).

## 3. 바닥 640장 → 벽지 1장

체커보드 바닥이 25pt짜리 타일 **640개**(32×20)로 깔려 있었습니다. 영원히 안 변하는 무늬인데도요. 이걸 **그림 한 장으로 미리 그려서**(사전 렌더) 노드 1개로 바꿨습니다. 화면에 보이는 결과는 픽셀 단위로 동일합니다.

비유: 욕실 바닥에 타일 640장을 한 장씩 붙이는 대신, 타일 무늬가 인쇄된 장판 한 장을 까는 것. 무늬가 안 바뀐다면 결과는 같고 관리는 1/640이죠.

## 4. TextureAtlasStore — 도장 공장 통일

캐릭터 그림(텍스처)을 만들어 보관하는 캐시 코드가 Player·Enemy·Professor·StoneGuard에 **거의 똑같이 4벌 복사**되어 있었습니다. R0에서 애니메이션 코드를 1벌로 합쳤는데(프로토콜), 캐시는 남아 있었죠. 이번에 `TextureAtlasStore` 한 곳으로 전부 흡수 — 이제 "그림을 만들고 보관하는 곳"은 게임 전체에 단 하나입니다.

**Spring으로 치면**: 서비스마다 제각각 `HashMap`으로 캐시하던 것을 싱글톤 캐시 매니저(`@Cacheable`) 하나로 모은 것. 캐시 정책(여기선 "픽셀이 또렷하게 보이는 .nearest 필터")도 한 곳에서 일괄 적용되니 빠뜨릴 수가 없습니다.

덤으로 벽 타일도 정리했어요. 타일 1개가 본체+그림자+하이라이트+테두리 = **노드 4개**였는데, 넷을 그림 한 장에 미리 합쳐 구워서(베이크) 1개로. 물리 충돌·벽 파괴 같은 동작 데이터는 한 글자도 안 건드렸습니다.

## 5. update 파이프라인 — 매 프레임의 순서표

게임의 심장 `update()`(초당 60번 실행)는 일 순서가 코드에 암묵적으로만 존재했습니다. 이걸 명시적 순서표로 고정했어요:

```
입력 → 플레이어 → AI → 투사체 → 충돌 → 연출 → 카메라 → HUD → 명단 청소
```

순서가 왜 중요하냐면 — 카메라는 플레이어가 움직인 **뒤에** 따라가야 하고, HUD 점수는 점수가 확정된 **뒤에** 그려야 합니다. 순서가 암묵적이면 나중에 코드를 끼워 넣다가 "카메라가 한 프레임 늦게 따라오는" 류의 미세 버그가 생겨요.

**Spring으로 치면**: 시큐리티 필터 체인입니다. 인증 필터가 인가 필터보다 먼저여야 하는 것처럼, 순서 자체가 사양인 코드는 순서를 **눈에 보이게** 박아둬야 합니다.

## 6. BGM 양자화 가드 — "조금 빨라져라"를 60번 외치지 않기

마지막 5초에 음악이 점점 빨라지는 연출이 있는데, 매 프레임 미세하게 다른 속도값(1.0001, 1.0002…)을 오디오 엔진에 전송하고 있었습니다. 사람 귀로는 구분도 안 되는 차이를요.

속도값을 0.01 단위로 반올림(양자화)하고, **반올림 결과가 직전과 다를 때만** 전송하게 바꿨습니다. 전송 ~300회 → 최대 16회. 들리는 결과는 동일합니다.

**Spring으로 치면**: 더티 체킹이에요. JPA가 필드가 실제로 바뀌었을 때만 UPDATE를 날리듯, "의미 있는 변화"가 있을 때만 외부 시스템을 호출합니다.

## 7. 이번 단계의 드라마 — 측정 기준과 원칙이 충돌하면?

합격 게이트 중 하나가 "화면 노드 수 ≤300"이었는데, **hard 난이도에서 ~368로 미달**이 났습니다. 원인을 파보니: hard는 F 폭탄이 최대 22발인데, 폭탄 1발이 가독성용 자식(빛 테두리 등) 2개를 데리고 다녀서 3노드 — 이 자식들은 "아슬아슬하게 스쳤을 때 번쩍이는 연출"이 따로 걸려 있어 그림 한 장으로 합치면 **연출이 바뀝니다**. 그런데 R1의 제1원칙이 "행동·연출 불변(위반=P0)"이었죠.

즉 **측정 기준(≤300)과 절대 원칙(불변)이 정면 충돌** — 둘 다 지킬 방법이 수학적으로 없었습니다. 결정: 절대 원칙이 이깁니다. 불변을 지키는 한도 내 최선(음표는 연출이 없는 정적 자식이라 합치기 가능 → 적용)을 다하고, hard 잔여분은 그 연출 자체를 재설계하는 다음 단계(R2 게임필)로 **기록을 남기고 이관**했습니다.

교훈 두 가지:
- **숫자 목표가 원칙과 충돌하면, 숫자를 몰래 맞추지 말고 충돌을 보고하라.** generator가 "384라서 미달입니다"를 숨기지 않고 정직하게 보고한 덕분에 올바른 결정이 가능했습니다. 미달을 감추고 합격 시늉을 했다면 R2에서 더 비싸게 터졌을 거예요.
- **이관은 기록이 전부** — "나중에 하자"는 기록이 없으면 영원히 안 합니다. REFACTOR_STATE에 R2 과제로 박아뒀습니다.

## 오늘의 핵심 교훈

1. **조회가 잦으면 변경 시점에 일하라** — 매 프레임 수색(enumerate) 대신 태어나고 죽을 때 명단(registry)을 갱신한다.
2. **재사용의 핵심은 빌려주기가 아니라 씻기** — 풀의 버그는 전부 reset 누락에서 나온다. 체크리스트로 전수 점검.
3. **원칙과 숫자가 충돌하면 원칙이 이기고, 충돌은 보고한다** — 정직한 미달 보고가 몰래 맞춘 합격보다 가치 있다.
