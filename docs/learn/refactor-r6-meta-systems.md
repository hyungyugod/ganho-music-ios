# 학습 노트 — 리팩토링 R6: 메타 시스템 (2026-06-11)

> 이번에 한 일: "한 판 더 하고 싶게 만드는" 장치들을 만들었습니다.
> 별 모으기, 별로 캐릭터 해금, 업적 16종, 매일 바뀌는 일일 도전,
> 그리고 이 모든 걸 저장하고 클라우드와 합치는 금고(Repository)까지요.
> 기존 유저의 최고 기록은 단 1바이트도 건드리지 않았습니다.

## 1. 지난 숙제 풀기 — 상수 두 벌을 공식 하나로

R5 노트 4번에서 "설계서 별 기준표(60/50/30)와 실제 목표 점수(70/50/40)가
어긋나서 경고만 남기고 R6로 미뤘다"고 했죠. 이번에 그 숙제를 풀었습니다.

방법이 재밌어요. **표를 고친 게 아니라 표를 없앴습니다.**

```
별 1개 = 목표 점수 그대로 (hard면 40)
별 2개 = 목표 × 1.3      (hard면 52)
별 3개 = 목표 × 1.6      (hard면 64)
```

숫자 표 두 벌이 있으면 언젠가 또 어긋납니다. 한쪽을 다른 쪽에서
**계산해 내면** 어긋날 수가 없어요. 그리고 R5에서 "넣는 순간 크래시"라
경고로 낮췄던 assert 검사를 이번엔 당당하게 다시 넣었습니다. 이제 진짜로 안 터지니까요.

**Spring으로 비유하면**: `application.yml`에 같은 값을 두 군데 적어두면
배포 때마다 한쪽만 고치는 사고가 나죠. 한 곳만 적고 나머지는
`@Value` 참조나 계산 프로퍼티로 만드는 것 — 단일 진실 원천(Single Source of Truth)입니다.

## 2. 래칫(ratchet) — 올라가기만 하는 톱니바퀴

별 기록은 난이도 3종 × 캐릭터 5명 = 15칸에 저장하는데, 규칙이 하나뿐이에요.

> **새 기록이 기존보다 높을 때만 쓴다. 낮으면 무시한다.**

공구 래칫 렌치가 한 방향으로만 돌아가듯, 이 저장칸은 절대 후진하지 않습니다.
클라우드에서 다른 기기 기록과 합칠 때도 같은 규칙(둘 중 큰 값)이라,
어떤 순서로 어떤 기기와 합쳐도 결과가 같아요. 합치는 순서를 걱정할 필요가 없습니다.

**Spring으로 비유하면**: `UPDATE score = GREATEST(score, :new)` 한 줄짜리 쿼리예요.
"읽고-비교하고-쓰는" 3단계로 짜면 동시 요청 때 레이스가 생기지만,
연산 자체를 단조 증가로 만들면 몇 번 실행돼도, 누가 먼저 와도 안전합니다.

## 3. 이사할 때 원본은 안 버린다 — 읽기 전용 마이그레이션

기존 유저는 이미 최고 점수·졸업 기록을 갖고 있어요. 새 별 시스템이
이 데이터를 **읽어서** 별 칸을 채워줍니다(백필). 여기서 철칙 세 가지:

1. **기존 저장칸에는 쓰기 금지** — 읽기만 한다. 원본 무손실.
2. **멱등** — 두 번 실행돼도 결과 동일 ("이미 했음" 버전 표시 확인 후 진행).
3. **새 데이터는 새 칸에만** — 새 키 5개 추가, 기존 키 0개 변경.

이번 QA에서 이걸 3중으로 검사했어요: 키 목록 비교(diff), 마이그레이션 전후
원본 바이트 비교, 그리고 앱을 4번 껐다 켜며 값이 유지되는지 실측.

**Spring으로 비유하면**: Flyway 마이그레이션이에요. `V2__add_stars.sql`은
새 테이블을 만들고 기존 테이블에서 SELECT만 하죠. 버전 테이블이 "이미 적용됨"을
기억해서 재시작해도 두 번 안 돌고요. 원본 DROP은 당연히 없습니다.

## 4. 어제도 오늘도 같은 주사위 — 날짜로 만드는 랜덤

일일 도전은 매일 6종 중 하나가 "랜덤"으로 걸립니다. 그런데 진짜 랜덤이면
앱을 껐다 켤 때마다 도전이 바뀌겠죠? 서버에서 정해주자니 서버가 없고요.

해결: **오늘 날짜(20260611)를 시드(씨앗)로 쓰는 가짜 랜덤**입니다.
같은 씨앗을 넣으면 항상 같은 결과가 나오는 수식(splitmix64)이라,
하루 종일 몇 번을 켜도 같은 도전이고, 자정이 지나면 자연히 바뀝니다.
100일치를 돌려보는 자동 검사로 "매일 같은 입력 = 같은 출력"을 증명했어요.

**Spring으로 비유하면**: `new Random(seed)`로 재현 가능한 테스트를 만들거나,
`hash(userId) % 100`으로 A/B 테스트 버킷을 나누는 것과 같아요.
"랜덤처럼 보이지만 입력이 같으면 결과도 같다" — 분산 환경에서 조율 없이
모두가 같은 답을 내게 하는 고전 기법입니다.

## 5. 테스트 프레임워크가 없으면 — 앱 안에 검사관을 심는다

"기존 기록 보존"은 깨지면 P0(최악)인데, 이 프로젝트엔 테스트 타겟이 없어요.
새로 만들자니 Xcode 프로젝트 파일 수술이 필요해서 위험 대비 이득이 안 나왔고요.

대안: **개발 빌드에만 들어가는 자가검증 파일** 하나를 만들었습니다.
환경변수 스위치를 켜고 앱을 실행하면 8가지 시나리오(T1~T8)를 자동으로 돌리고
콘솔에 `PASS 8/8`을 찍어요. 중요한 안전장치 두 가지:

- **격리된 모래상자** — 진짜 저장소가 아닌 별도 공간에서 검사하고, 끝나면 통째로 삭제.
- **릴리즈에서 완전 증발** — `#if DEBUG`로 감싸서 출시 앱에는 코드 자체가 없음.

**Spring으로 비유하면**: 테스트 모듈이 없는 레거시에서 `@Profile("selftest")`
러너를 만들고 H2 인메모리 DB로 검증하는 것과 같아요. 운영 DB는 안 건드리고,
운영 빌드에는 그 빈(bean)이 아예 등록되지 않죠.

## 6. 구버전 앱과 싸우지 않기 — optional 필드로 스키마 키우기

클라우드 저장 데이터에 메타 정보(별·업적·일일 도전)를 추가해야 했는데,
구버전 앱이 올려둔 데이터에는 그 필드가 없어요. 필수 필드로 추가하면
구버전 데이터를 읽다가 실패합니다.

그래서 **있어도 되고 없어도 되는(optional) 필드**로 추가했어요.
- 구버전 데이터를 읽으면 → 메타 없음 → 빈 값으로 시작 (에러 아님)
- 신버전 데이터를 구버전 앱이 읽으면 → 모르는 필드 무시 (원래 동작 유지)

기존 저장 함수들의 모양(시그니처)도 그대로 두고, 새 인자에 기본값을 줘서
기존 호출부 수정 0줄로 끝냈습니다.

**Spring으로 비유하면**: 운영 중인 API의 DTO에 필드를 추가할 때
`@JsonInclude(NON_NULL)` + 기본값으로 하위 호환을 지키는 것과 같아요.
"필수로 추가"는 사실상 모든 클라이언트에 대한 파괴적 변경(breaking change)입니다.
