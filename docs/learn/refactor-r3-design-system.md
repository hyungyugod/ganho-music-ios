# R3 학습 노트 — 디자인 시스템 인프라 (화면을 바꾸기 전에 부품 공장부터)

> 그랜드 리팩토링 v3의 네 번째 단계. R4·R5에서 메뉴 화면들을 전부 갈아엎을 예정인데, R3는 그 전에 **색·글꼴·간격의 규칙집과 조립식 UI 부품**을 먼저 만들어두는 단계입니다. 화면은 거의 안 바뀌었는데(전환 연출만 바뀜) 파일은 11개가 늘었어요. 공장을 지은 거지 제품을 낸 게 아니거든요.

## 오늘 한 일 한 줄 요약

색 14개·글꼴 7벌·간격 7단을 "토큰"이라는 이름의 상수로 박제하고, 픽셀풍 버튼·카드·다이얼로그 등 부품 7종을 만들고, 화면 전환을 SceneRouter 한 파일로 모았으며(밋밋한 fade 폐기), 부품을 한눈에 보는 DEBUG 전용 전시장을 달았습니다. 게임 규칙·기존 화면 레이아웃은 0줄 변경.

## 1. 디자인 토큰 — "이 가게의 빨강은 이 빨강 하나"

지금까지는 화면마다 "코랄빛 빨강"을 각자 적당히 찍어 썼습니다. 그러면 화면 10개를 리뉴얼할 때 빨강이 10가지가 돼요. 그래서 **색 14개·글꼴 7벌·간격 7단·레이어 11층·모션 시간 7개**에 전부 이름을 붙여 Config 파일에 박았습니다. 앞으로 화면을 만들 땐 "#FF6E5A"라고 쓰는 게 금지고, `Palette.coral`이라고 써야 합니다. 색을 바꾸고 싶으면 한 줄만 고치면 전 화면이 따라옵니다.

**Spring으로 치면**: 컨트롤러마다 DB 주소를 하드코딩하지 않고 `application.yml` 한 곳에 두는 것과 같습니다. 디자인 시스템은 말하자면 **UI의 설정 중앙화**예요. 매직 넘버 금지 규칙이 색상에도 그대로 적용된 겁니다.

중요한 제약 하나: 기존 상수는 **건드리지 않고 추가만** 했습니다. 기존 화면들이 아직 옛 상수를 쓰고 있으니까요. 옛 화면이 v3 부품으로 갈아타는 건 R4·R5의 일이고, 그때 참조가 0이 된 옛 상수를 지웁니다. 마이그레이션은 "새 길 깔기 → 갈아타기 → 옛 길 철거" 순서지, 옛 길부터 부수면 안 돼요.

## 2. 컴포넌트 키트 — 조립식 부품은 못이 박힌 채로 팔지 않는다

버튼·패널·칩·진행바·카드·다이얼로그 6종 + 밤하늘 배경 1종을 부품으로 만들었습니다. 규칙은 하나: **부품은 자기가 어느 화면에 놓일지 몰라야 한다**(씬 비의존). 부품 생성자에 "어느 씬이냐"가 들어가는 순간 그 화면 전용 부품이 되고, 재사용은 끝납니다.

**Spring으로 치면**: 공통 라이브러리 모듈에 특정 서비스의 `@Autowired`를 넣지 않는 원칙입니다. 부품은 파라미터(텍스트·변형·콜백)만 받고, 조립은 화면이 합니다 — DI의 방향이 항상 바깥→안쪽인 것처럼요.

## 3. SceneRouter — 화면 전환 13곳이 제멋대로면 누구도 책임지지 않는다

화면 전환 코드가 13곳에 흩어져 각자 fade를 쓰고 있었습니다. 이걸 `SceneRouter` 한 파일로 모으고, 전환을 딱 3종(앞으로 push / 뒤로 push / 게임 진입 픽셀 디졸브)으로 통일했습니다. 이제 `SKTransition`을 만들 수 있는 파일은 프로젝트에 하나뿐이고, grep 한 줄로 위반을 잡을 수 있어요.

**Spring으로 치면**: 모든 요청이 API Gateway를 지나게 하는 것과 같습니다. 인증을 컨트롤러 40개가 각자 하면 하나는 꼭 빼먹죠. 횡단 관심사(전환 연출은 UI의 횡단 관심사입니다)는 한 관문으로 모아야 정책 변경이 한 줄이 됩니다.

덤 — **픽셀 디졸브의 비밀**: 화면이 픽셀 블록으로 부서지는 연출인데, 블록만큼 노드를 만들면 수백 노드가 생깁니다. 대신 화면을 덮는 스프라이트 **1장**에 셰이더(GPU에서 도는 작은 프로그램)를 입히고, 매 프레임 진행도 숫자 1개만 올려줍니다. 부서지는 계산은 GPU가 픽셀별로 알아서. CPU에서 루프 돌리지 말고 그 일에 특화된 엔진에 내리라는 점에서, 애플리케이션에서 for문 돌리지 말고 SQL 한 방으로 DB에 시키는 것과 같은 원리입니다.

## 4. 폰트 fallback 체인 — 없을 수도 있는 것에 기대면 무너진다

픽셀 글꼴 Galmuri를 새로 넣었는데, "폰트 파일이 확보된다"를 전제로 코드를 짜면 확보 실패 시 빌드가 깨집니다. 그래서 **Galmuri → DungGeunMo → Jua(번들 보장)** 순서로 폴백 체인을 만들었어요. 최악의 경우에도 시스템 기본 글꼴이 노출되는 일은 없습니다.

**Spring으로 치면**: `@Value("${font.name:기본값}")`의 그 콜론입니다. 외부 의존(설정·파일·원격 서비스)에는 항상 "없으면 이걸로"가 한 단계는 있어야 부팅이 안 죽어요.

## 5. DEBUG 갤러리 — 부품 전시장은 손님 매장에 내지 않는다

부품 7종을 한 화면에 전부 늘어놓은 전시장 씬을 만들었습니다. 환경변수 하나로 부팅하면 버튼 3변형·칩 3변형·진행바 애니메이션까지 한눈에 보여요(스크린샷으로 60fps 실증). 핵심은 이 파일 **전체가 `#if DEBUG`로 감싸여** 릴리즈 빌드에는 바이트 하나 안 들어간다는 것.

**Spring으로 치면**: Swagger UI나 actuator를 `dev` 프로파일에만 여는 것과 같습니다. 프론트엔드 진영의 Storybook을 SpriteKit으로 만든 셈이에요 — 부품을 실제 화면에 꽂기 전에 단독으로 검수할 수 있게.

## 6. 설계서도 틀린다 — "코드가 진실" 원칙이 실전에서 작동한 날

설계서(SPEC)에 "이 프로젝트는 폴더 동기화 방식이라 새 파일을 만들면 자동으로 빌드에 포함된다 — 프로젝트 파일 수동 편집 금지"라고 적혀 있었습니다. 구현 담당이 실제로 확인해 보니 **사실이 아니었어요**. 소스 폴더는 동기화 그룹이 아니어서 명시 등록 없이는 컴파일 자체가 안 됩니다. 구현 담당은 지시를 어기는 대신 ① 코드 현실을 증거(프로젝트 파일 몇 번째 줄, 과거 파일들의 등록 방식)와 함께 기록하고 ② 기존 컨벤션과 같은 방식으로 등록한 뒤 ③ 빌드 성공으로 실증했고, 검수 담당이 그 증거를 재확인해 "필수적 이탈"로 승인했습니다.

**교훈**: 문서와 코드가 싸우면 코드가 이깁니다. 단, 이기는 쪽도 **증거를 남겨야** 합니다. 말없이 어기면 규율 붕괴고, 증거와 함께 어기면 문서 개선이에요.

## 7. "내 탓인가?"를 증명하는 법 — 베이스라인 재현

Release 빌드가 컴파일러 충돌로 실패했습니다. 내 변경 때문일까요? 검수 담당의 확인 절차가 교과서적입니다: `git stash`로 이번 변경을 전부 치워둔 **직전 커밋 상태**에서 같은 빌드를 돌리니 — 같은 지점에서 같은 충돌. 즉 이 문제는 R3 이전부터 있었고(R1 산물인 ObjectPool 관련), R3의 책임이 아님이 증명됐습니다. 물론 치워둔 변경은 `stash pop`으로 복원 확인까지.

**Spring으로 치면**: "이 테스트, 내 브랜치에서만 깨져요?"라는 질문에 main 체크아웃해서 돌려보는 그것입니다. 귀책을 가리는 가장 싼 방법은 **변경 전 상태에서의 재현**이에요. 다만 "내 탓 아님"이 "고칠 필요 없음"은 아니라서, 출시(아카이브)를 막는 문제니 R4 전에 고치기로 이관 기록을 남겼습니다.

## 오늘의 핵심 교훈

1. **리뉴얼은 부품 공장부터** — 화면 10개를 고치기 전에 토큰과 컴포넌트를 먼저. 안 그러면 빨강이 10가지가 된다.
2. **횡단 관심사는 관문 하나로** — 전환 13곳을 1파일로. 위반이 grep 한 줄로 잡히는 구조가 좋은 구조다.
3. **외부 의존에는 폴백 한 단계** — 폰트든 설정이든 "없으면 이걸로"가 있어야 무너지지 않는다.
4. **문서를 어길 땐 증거와 함께** — 코드가 진실이지만, 진실임을 보이는 건 어긴 쪽의 책임이다.
5. **귀책은 베이스라인 재현으로 가린다** — stash 한 번이 "아마 제 탓 아닐걸요"보다 백 배 강하다.
