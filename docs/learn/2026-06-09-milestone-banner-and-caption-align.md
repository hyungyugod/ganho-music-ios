# 추측하지 말고 "재보기" — 캐릭터 발밑에 글자 맞추기 + 끊기지 않는 응원 배너

## 한 줄로

"Apple 연동됨" 글자를 캐릭터 몸 아래선에 딱 맞추려고 좌표를 **때려 맞추는 대신, 캐릭터 그림이 실제로 어디서 끝나는지 자로 재서**(`calculateAccumulatedFrame`) 그 높이에 글자 바닥을 붙였어. 목표 점수는 easy 70 / normal 50 / hard 40으로 (지난번 내가 하/상을 거꾸로 본 걸 바로잡음). 그리고 게임을 **1초도 멈추지 않고** 화면 위를 스윽 지나가는 "절반 왔어요!" "10점만 더!" 응원 배너를 새로 만들었어.

## 문제 1 — 글자를 캐릭터 발밑에 맞추기: 추측 ❌ 측정 ⭕

네가 "글자 아랫부분이 옆 캐릭터 몸 아래선과 같은 높이였으면" 했잖아. 이걸 하는 두 가지 방법이 있어:

- **나쁜 방법(추측)**: "캐릭터가 화면 중앙쯤 있고 키가 한 200쯤 되니까, 발밑은 대충 y=150이겠지?" → 폰 크기 바뀌면 와장창 어긋남.
- **좋은 방법(측정)**: SpriteKit한테 **"이 캐릭터 그림, 화면에서 실제로 어디부터 어디까지 차지해?"** 하고 물어봄. 그게 `calculateAccumulatedFrame()`이야. 자식(머리·어깨 등)을 다 감싼 **진짜 네모 상자**를 돌려줘. 그 상자의 **바닥(minY)**이 곧 "몸 아래선"이지. 거기에 글자 바닥을 갖다 붙이면 폰이 크든 작든 항상 정확해.

> **Spring 비유**: 리스트 개수를 `int count = 10;` 하고 하드코딩하는 거랑, `list.size()`로 **실제 값을 물어보는** 거의 차이야. 데이터가 바뀌면 하드코딩은 거짓말이 되지만 `size()`는 늘 맞아. **매직넘버로 추측하지 말고, 실제 상태를 측정**해서 거기에 맞춰라 — 이게 핵심.

### 곁들인 함정 — "누가 먼저 자리를 정하느냐" (순서 의존)

이제 줄세우기가 **아바타 → 글자 → 시작버튼** 순서가 됐어. 글자는 아바타 위치를 보고 정해지고, 버튼은 그 글자 위에 붙거든. 그러니 **아바타 자리부터 정해진 다음에** 글자를 재고, **글자가 정해진 다음에** 버튼을 올려야 해. 순서가 꼬이면 글자가 "아직 안 정해진 아바타"를 읽어서 엉뚱한 곳에 가.

> **Spring 비유**: 빈(bean) 초기화 순서 같은 거야. A가 B를 의존하면 B가 먼저 만들어져야 하잖아. 여기선 `layoutNurseAvatar()` → `layoutAuthCaption()` → `layoutStartButton()` 순서를 화면 등장(`didMove`)·화면 크기 변경(`didChangeSize`) **양쪽 모두에서** 똑같이 맞췄어.

## 문제 2 — 목표 점수, 그리고 "하/중/상 vs easy/normal/hard"

이게 지난번 헷갈렸던 지점이야. 게임 **코드 속 이름**은 영어(`easy`/`normal`/`hard`)인데, **화면에 보이는 라벨**은 한글(하/중/상)이야. 그리고 매핑이:

- `easy` = **하** (낮음) = 70
- `normal` = **중** = 50
- `hard` = **상** (높음) = 40

지난번 네가 "상 70…"이라 했을 때 내가 상=hard로 봤는데, 이번에 영어로 콕 집어줘서 **"하(easy)가 70, 상(hard)이 40"** 으로 바로잡았어. 어려운 모드일수록 목표가 낮은 건, 하드는 살아남기 힘드니 40점이 진짜 도전이고, 이지는 술술 모이니 70점이 적당하다는 뜻으로 이해했어.

> **Spring 비유**: enum의 **내부 이름(`name()`)과 표시 이름(`getDisplayName()`)이 다른** 전형적 케이스야. `Status.DONE` 인데 화면엔 "완료"로 보이는 것처럼. 코드 이름만 보고 "상=hard니까 높은 값" 같은 직관을 적용하면 틀려. **이름과 라벨을 헷갈리지 말고 매핑표를 직접 확인**해야 해.

고친 건 딱 한 줄. 목표 점수가 **한 군데(`targetScoreByDifficulty`)에만** 적혀 있고 결과창·난이도화면이 다 거기서 읽어가서, 그 줄만 바꾸면 끝이야.

## 문제 3 — 끊기지 않는 응원 배너 (신규 기능)

"목표 절반 도달, 10점 남음에 화면 위에 살짝 떴다 사라지는 안내"를 만들었어. 신경 쓴 포인트 3가지:

### (1) "한 번만" 띄우기 — 멱등성

배너 검사는 매 프레임(초당 60번) 도는 게임 루프 안에 있어. 가만 두면 "절반 넘음"이 60번 다 참이라 배너가 60장 겹쳐 떠. 그래서 **"이미 띄웠음" 체크박스(Bool)** 를 둬서, 한 판에 딱 1번만 뜨게 했어.

> **Spring 비유**: **멱등성 키(idempotency key)** 야. 결제 요청이 네트워크 때문에 10번 와도 **딱 1번만** 결제되게 하는 그거. "이미 처리함" 표시를 보고 두 번째부터는 무시하는 거지.

### (2) `==` 말고 `>=` 로 "선을 넘었나" 보기

점수는 콤보 때문에 한 번에 +1~+4씩 **껑충껑충** 올라. 그래서 목표 절반이 25점이어도 점수가 정확히 25에 안 멈추고 24→27로 건너뛸 수 있어. `점수 == 25`로 검사하면 그냥 지나쳐버려. 그래서 **`점수 >= 25`(선을 넘었나)** 로 봤어.

> **Spring 비유**: SLA 임계치 감시랑 같아. "요청이 정확히 1000개일 때"가 아니라 **"1000개를 넘어섰나"** 를 봐야지. 점(точка)이 아니라 **선(임계선)** 으로 판단.

### (3) 화면에 "붙은" UI + 게임 안 멈춤

배너는 **카메라에 붙여**(cameraNode 자식) 놨어. 그래서 캐릭터가 맵을 돌아다녀도 배너는 화면 위에 **고정**돼. (맵에 붙이면 같이 흘러가버려.) 그리고 박병장 등장컷처럼 화면을 어둡게 깔거나 멈추는 거 없이, **그냥 글자만 스윽 나타났다 사라져** — 네가 말한 "게임 방해 안 하는 선".

> **Spring 비유**: 카메라에 붙인 UI = CSS `position: fixed` 헤더 같은 거(스크롤해도 안 움직임). 그리고 점수 올라가는 곳이 여러 군데(노트·변기보너스 등)라, 거기마다 검사를 넣는 대신 **게임 루프 한 곳에서만** 검사했어 — 컨트롤러마다 코드 박는 대신 **인터셉터(AOP) 한 곳**에 두는 거랑 같아. 빠뜨릴 일이 없지.

### (4) 새 파일은 "출석부"에 등록해야 빌드됨

새 배너 파일(`MilestoneBannerNode.swift`)을 만들고 끝이 아니라, Xcode 프로젝트 **출석부(project.pbxproj)** 4군데에 "얘도 우리 반이야"라고 등록해야 빌드에 껴. 안 하면 "그런 거 없는데?(Cannot find in scope)" 에러.

> **Spring 비유**: `@Component` 클래스 새로 만들었는데 **컴포넌트 스캔 범위 밖 패키지**에 둬서 빈 등록이 안 되는 거랑 똑같아. 파일만 있다고 자동으로 잡히는 게 아니야.

## 어떻게 작업했나 (하네스)

설계자 → 구현자 → 검수자. 검수 **합격 9.15/10**, 빌드 `BUILD SUCCEEDED`. 끝나고 나도 grep으로 목표값·신규 토큰·pbxproj 등록·레이아웃 순서를 직접 다시 확인했어.

## 손댄 파일

## 한 줄 교훈

**좌표는 추측하지 말고 재라.** 화면에 실제로 그려진 상자를 측정해서 거기에 맞추면, 어떤 폰에서도 안 어긋난다 — `calculateAccumulatedFrame()`은 그 "자(尺)"다.
