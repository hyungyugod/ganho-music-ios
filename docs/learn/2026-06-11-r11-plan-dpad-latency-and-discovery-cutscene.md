# R11 계획 노트 — D-Pad가 늦게 꺾이는 이유 & 박병장 컷씬은 조립만 하면 되는 이유

> 2026-06-11. 코드는 한 줄도 안 바꾼 **진단 세션**입니다. R10 끝나고 실제로 플레이해 보니
> ① D-Pad가 명령보다 늦게 꺾이고 ② 박병장 등장이 "잠깐 멈추고 보는 컷씬"이 아니어서,
> 왜 그런지 코드를 끝까지 추적해 R11 작업 계획으로 정리했습니다.

---

## 1. D-Pad가 늦게 꺾이는 이유 — "처음 출발만 빠르고, 꺾는 건 느린" 스무딩

### 무슨 일이 있었나

R10에서 D-Pad에 **스무딩**(부드럽게 따라가기)을 넣었습니다. 손가락이 살짝 떨려도
캐릭터가 덜덜거리지 않게 하는 장치였죠. 그때 "첫 입력은 즉시 반응"이라는 안전장치도
같이 넣었다고 했는데… 알고 보니 이 안전장치는 **멈춰 있다가 출발할 때만** 작동했습니다.

```
멈춤 → 오른쪽   : 즉시 출발 ✅ (안전장치 작동)
오른쪽 → 위로 꺾기 : 80ms 천천히 따라옴 ❌ (안전장치 미작동!)
```

게임에서 제일 많이 하는 행동이 "달리다가 방향 꺾기"인데, 정확히 그 동작만 느렸던 겁니다.

### Spring 비유

`@Cacheable`을 붙였는데 **캐시 갱신 조건을 "데이터가 없을 때"로만** 잡은 상황과 같습니다.
처음 조회(콜드 스타트)는 빠르게 채워주지만, 이미 값이 있는 상태에서 원본이 바뀌면
TTL이 끝날 때까지 옛날 값을 계속 보여주는 거죠. "비어있을 때만 특별 취급"이라는 조건이
실제로 제일 흔한 경로(값이 이미 있는데 바뀌는 경우)를 빼먹은 겁니다.

### 숫자로 보면

- 80ms 스무딩은 "63%만 따라오는 데 80ms"라는 뜻 — **완전히** 따라오려면 약 0.34초.
- 게다가 두 방향의 중간값을 지나는 동안 **속도 자체도 줄어듭니다**. 90° 꺾으면 순간적으로
  속도 29% 손실, 180° 반대로 꺾으면 거의 0(잠깐 멈춤)까지 떨어집니다.
- 얼굴(facing)과 조이스틱 노브는 즉시 도는데 몸만 늦게 따라와서, "이미 옆을 보는데
  몸은 미끄러지는" 장면이 보입니다. 이게 체감 지연을 실제보다 크게 만듭니다.

### 고치는 방법 (R11에서)

스무딩을 다 빼면 원래 막으려던 "덜덜거림"이 돌아옵니다. 그래서 **크게 꺾는 것만 즉시,
미세한 떨림만 스무딩**하는 각도 문턱을 둡니다:

```
두 방향의 차이가 60° 이상  → 즉시 꺾기 (의도적인 조작)
60° 미만                → 지금처럼 부드럽게 (손떨림 흡수)
```

Spring으로 치면 캐시에 **"원본 변경 이벤트가 오면 즉시 evict"** 조건을 추가하는 것과
같습니다. TTL(스무딩)은 그대로 두되, 명백한 변경 신호는 기다리지 않고 반영하는 거죠.

## 2. 박병장 컷씬 — 부품이 전부 창고에 있었다

### 현재 상태

박병장 등장은 두 가지인데, **둘 다 게임이 멈추지 않습니다**:

| 경로 | 트리거 | 현재 연출 |
|---|---|---|
| 이스터에그 (easy/normal) | 석조무사를 만지면 | "나와라 박병장!" 1.8초 + 공습 — 그동안 계속 조작 중 |
| 데뷔 (hard) | 30초 또는 50점 | 2.2초 오버레이 + 8초 무대 횡단 — 역시 게임 진행 중 |

"사실 석조무사의 친구로 실습생을 도와준다"는 이야기는 어디에도 문장으로 안 나옵니다.
말풍선 두 줄("왔는가, 병장." / "맡겨라, 친구!")이 최대였죠.

### 반가운 발견 — 잠자는 부품들

코드를 뒤져보니 필요한 부품이 **전부 이미 있었습니다**:

1. **카피(대사)**: `FeelTuning.swift`에 "사실 박병장은 석조무사의 오랜 친구입니다.
   석조무사가 조용히 신호를 보내자, 박병장이 나타나 잠시 수간호사를 물리쳐 줍니다."라는
   문구가 **정의만 되고 한 번도 안 쓰인 채** 잠들어 있었습니다. 원하는 서사 그대로요.
2. **멈춤 장치**: 게임 상태를 `.cutscene`으로 바꾸면 45초 타이머까지 같이 멈추는 구조가
   이미 있고(인트로 컷씬이 쓰는 방식), 일시정지 메뉴가 쓰는 "월드 정지 + 물리 정지 +
   입력 차단" 3종 세트도 검증돼 있습니다.
3. **컷씬 화면**: 제목+본문+"탭하면 계속" 오버레이(CutsceneOverlayNode)도 완성품이 있습니다.

Spring 비유: 새 기능을 만들려고 봤더니 **필요한 Bean이 전부 이미 등록돼 있고**,
심지어 딱 맞는 설정값이 `application.yml`에 주석 처리된 채 잠들어 있는 상황입니다.
새로 짜는 게 아니라 `@Autowired`로 조립만 하면 됩니다.

### 함정 하나 — "카메라에 붙은 연출은 멈춰도 계속 논다"

이 프로젝트의 동결 방식은 **월드(worldNode)만 멈추고 카메라(cameraNode)에 붙은 것들은
계속 움직이게** 설계돼 있습니다(그래야 일시정지 다이얼로그가 떠 있는 동안에도 버튼
애니메이션이 살아있으니까요). 그런데 박병장 공습(비행기·폭탄)이 카메라 쪽에 붙어 있어서,
컷씬으로 게임을 멈춰도 **공습은 화면 뒤에서 혼자 진행**돼 버립니다.

→ 해결: 공습 시작을 "컷씬을 탭으로 닫은 다음"으로 옮긴다. 읽기 끝 → 그 다음에 쇼.

Spring 비유: `@Transactional` 안에서 이벤트를 발행했는데 리스너가 `@Async`라
**트랜잭션이 끝나기 전에 이미 실행**돼 버리는 문제와 같습니다. 해결책도 같아요 —
`@TransactionalEventListener(phase = AFTER_COMMIT)`처럼 "끝난 다음에 시작"으로
순서를 바꾸는 겁니다.

## 오늘의 교훈

1. **"즉시 반응" 같은 보장은 어느 경로에 적용되는지까지 확인해야 한다.** "첫 입력 즉시"는
   참이었지만, 사용자가 제일 많이 쓰는 경로(이동 중 꺾기)는 그 보장 밖이었다.
2. **두 개의 좋은 튜닝이 합쳐져 나쁜 결과를 낼 수 있다.** 스냅을 관대하게(±41°) + 스무딩
   추가, 각각은 합리적이었지만 스냅이 방향을 90° 점프로 만들어 스무딩이 항상 최악 조건으로
   일하게 됐다.
3. **새 기능 전에 창고부터 뒤져라.** 원하는 대사가 미사용 상수로, 멈춤 장치가 검증된
   패턴으로 이미 있었다. 조사 없이 바로 짰으면 같은 걸 두 벌 만들 뻔했다.
