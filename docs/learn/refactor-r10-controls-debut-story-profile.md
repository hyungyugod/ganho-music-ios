# 학습 노트 — R10: 조작감·연출·스토리 + 프로필 리디자인 (2026-06-11)

> 이번에 한 일: 게임 "안"을 다듬는 단계였습니다. D-Pad 조작을 더 시원하고 부드럽게
> 고쳤고, 박병장 등장 연출에 효과음·도장 찍기·카메라 킥을 얹었고, 박병장과 석조무사가
> "오랜 친구"라는 작은 이야기를 심었습니다. 그리고 사용자 요청으로 프로필 창을
> 리디자인해서 로그아웃·계정 삭제 버튼을 별도 방으로 격리했습니다. QA 한 번에 합격(9.3/10).

## 1. "부드럽게"는 매 프레임 조금씩 따라가기 — 단, 시계로 재면서

D-Pad 방향을 휙 바꿀 때 캐릭터가 너무 뚝뚝 끊겨 보였어요. 해법은 **스무딩**:
입력이 가리키는 방향(target)으로 한 번에 점프하지 않고, 매 프레임 조금씩 다가갑니다.

여기서 함정 하나. "매 프레임 10%씩 다가가자"라고 하면, 60fps 기기에선 1초에 60번,
40fps로 버벅이는 기기에선 40번만 다가가요. **같은 게임인데 기기마다 조작감이 달라집니다.**

그래서 비율을 고정하지 않고 **프레임 사이에 흐른 실제 시간(dt)** 으로 계산합니다:

```swift
let alpha = 1 - exp(-dt / 0.08)   // 0.08초 = 따라잡기 시간 상수
smoothed += (target - smoothed) * alpha
```

`exp`가 들어간 이 식은 "0.08초쯤 지나면 거의 다 따라잡는다"를 **어떤 fps에서도 동일하게**
보장해요. Spring으로 비유하면 — 재시도 간격을 "루프 횟수"가 아니라 **시계 기준**으로
잡는 것과 같습니다. 루프가 빨리 돌든 늦게 돌든 1초는 1초니까요.

그리고 조작감의 진짜 핵심은 따로 있었습니다: **시작은 즉시, 변화만 부드럽게.**
- 멈춰 있다가 처음 움직일 때 → 스무딩 없이 **즉시** 출발 (여기 80ms를 끼우면 "굼뜬 게임"이 됨)
- 이동 중 방향을 틀 때 → 80ms 스무딩
- 손을 뗄 때 → **즉시** 정지

"부드러움"을 어디에 적용하고 어디엔 적용하지 **않을지**가 수치보다 중요했어요.

## 2. 가공은 소비하는 쪽에서 — 원본 데이터는 건드리지 않는다

스무딩을 D-Pad 노드 안에 넣을 수도 있었어요. 그런데 D-Pad의 방향값은 이동만 쓰는 게
아닙니다. 돌진 스킬의 방향, 캐릭터가 바라보는 얼굴(facing)도 같은 값을 읽어요.
D-Pad 안에서 값을 뭉개버리면 돌진까지 80ms 늦게 반응하는 부작용이 생깁니다.

그래서 스무딩은 **이동 코드(MovementInput) 안에서만** 적용했습니다. D-Pad가 내놓는
원시값은 그대로 두고요. 실제로 이번 작업에서 DPadNode·Direction·PlayerNode 파일은
**한 줄도 안 바뀌었습니다** (git diff 0).

Spring 비유: Entity의 필드를 화면 사정에 맞춰 직접 바꾸지 않고, 화면에 내보내는
DTO에서 가공하는 것과 같아요. 원본을 건드리면 그 원본을 믿는 다른 코드가 전부 영향을 받습니다.

## 3. 문서에 적힌 기능이 코드에서 불가능할 수 있다 — 계획 단계에서 잡아야 싸다

백로그에는 "데뷔 컷씬을 **석조무사가 같이 있을 때** 분기해서 우정 서사로"라고 적혀
있었어요. 그런데 계획 담당(planner)이 코드를 추적해 보니 — 박병장 데뷔는 hard 난이도
전용인데, **석조무사는 hard에 아예 등장하지 않습니다.** 두 명이 같은 화면에 있는 순간
자체가 존재하지 않아요. 문서만 믿고 구현을 시작했다면 중간에 멈췄겠죠.

그래서 설계를 바꿨습니다: 같은 화면에 없어도 성립하는 **"무전(라디오) 서사"** —
컷씬 카피를 "석조무사의 무전 — 오랜 친구 / 박병장, 지원 출격!"으로 바꾸고, 컷씬 안에
석조무사 얼굴을 카메오로 띄웠어요. 우정이라는 목표는 지키고 수단만 바꾼 겁니다.

교훈: **문서와 코드가 다르면 코드가 진실.** 그리고 이런 모순은 코드를 짜기 전,
계획 단계에서 발견할수록 쌉니다.

## 4. 위험한 버튼은 "다른 방"으로 — 격리는 새 화면이 아니라 모드 전환으로

사용자 요청의 핵심: 프로필 창에서 로그아웃·계정 삭제가 다른 버튼들과 섞여 보기 어렵다,
**최대한 안 보이게 해달라.**

UI 설계 원칙으로 번역하면 — *자주 쓰는 것은 가깝게, 위험한 것은 멀게.* 이전(R9)에는
버튼을 작게 만들어 같은 창 맨 아래에 뒀는데, 작아도 **같은 방에 있으면** 눈에 들어오고
잘못 누를 수 있어요. 이번엔 아예 **방을 분리**했습니다:

- 프로필 창: 이름 편집·[기록]·[업적] + 맨 아래 조그만 [계정 관리] 한 줄만
- [계정 관리]를 눌러야만 나오는 서브 화면: 로그아웃·계정 삭제 (+뒤로)

구현은 새 다이얼로그를 만들지 않고, **한 다이얼로그 안에서 모드를 갈아끼우는** 방식
(설정 다이얼로그의 '크레딧 보기' 전환과 동일 패턴). 모드가 바뀔 때 기존 버튼을 전부
지우고 새로 만들어서, 안 보이는데 터치만 살아 있는 "좀비 버튼"이 0개임을 보장합니다.

Spring 비유: 같은 URL에서 파라미터로 뷰만 바꾸는 게 아니라, 관리자 기능을
`/admin` 하위로 빼고 진입 링크 하나만 남기는 것. 단 — **삭제 직전의 "정말요?" 확인
다이얼로그는 그대로 보존**했어요. 숨기는 것과 보호 절차를 빼는 것은 다른 문제입니다.

## 5. 연출 강화는 "위에 얹기" — 기존 시계는 1초도 건드리지 않는다

박병장 데뷔 연출에 효과음(스팅어)·토스트 도장 찍기·카메라 킥·체류 셰이크를 추가했지만,
기존 컷씬의 2.2초 타이밍과 완료 콜백(completion) 위치는 **diff 0** — 한 줄도 안
바뀌었습니다. 새 연출은 전부 기존 타임라인의 특정 시점에 **병행으로 얹은** 것뿐이에요.

왜 이렇게까지? 그 2.2초 뒤에는 "컷씬 끝나면 박병장 실제 등장 → 8초 체류 → 퇴장"이라는
약속의 사슬이 걸려 있어요. 타이밍을 1초라도 늘리면 사슬 전체가 흔들립니다.
Spring 비유: 잘 돌아가는 트랜잭션 흐름 한가운데에 로직을 끼워 넣지 않고,
이벤트 리스너를 달아 부수 효과만 추가하는 것.

효과음도 규칙이 있었어요 — 게임 도중에 소리를 실시간 합성하면 프레임이 떨립니다.
그래서 모든 효과음은 **앱 시작 때 미리 렌더링**해 두고, 게임 중엔 재생만 합니다
(서버 기동 때 캐시 워밍업하고 요청 처리 중엔 캐시만 읽는 것과 같아요).

## 6. 구현을 바꿨으면 주석도 같이 — 주석은 미래의 나에게 보내는 명세

이번 QA에서 잡힌 자잘한 결함 하나: 효과음 주석에는 "G2·G2·C3 세 음(빰·빰·빠암)"이라고
적혀 있는데 실제 구현은 **두 음(G2→C3)**이었어요. 작업 중에 설계가 바뀌었는데 주석이
따라오지 못한 겁니다. 코드는 멀쩡히 돌아가니 컴파일러는 아무 말도 안 해요.

이게 왜 문제냐면 — 6개월 뒤 누군가(아마 미래의 나) 이 소리를 고치려고 주석을 읽으면,
**세 음짜리 구조를 찾으며 헤매게 됩니다.** 거짓말하는 주석은 주석이 없는 것보다 나빠요.
이번 단계에서는 명세 문서(02_GAME_FEEL)도 코드 변경과 **같은 커밋에서** 갱신하는 걸
합격 조건으로 걸었는데, 주석 한 줄이 그 그물을 빠져나갔다가 QA에서 잡혔습니다.
