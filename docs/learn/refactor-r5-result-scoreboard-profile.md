# 학습 노트 — 리팩토링 R5: 결과·기록·프로필 재구축 (2026-06-10)

> 이번에 한 일: 게임이 끝나면 나오는 결과 화면, 최고 기록표(스코어보드),
> 프로필/계정 팝업을 새 픽셀 디자인으로 완전히 새로 만들었습니다.
> 1,327줄짜리 결과 화면이 600줄이 됐고, 옛 부품 5개를 또 쓰레기통으로 보냈어요.

## 1. 결과 화면은 "영화 콘티"다 — 연출 시퀀스

새 결과 화면은 정보를 한꺼번에 다 보여주지 않아요. 시간표대로 하나씩 등장합니다.

```
0.0초  "졸업!" 도장이 쾅 (커졌다 작아지며 + 화면 흔들림 + 도장 소리)
0.4초  점수가 0부터 드르륵 올라감 (틱틱틱 소리도 점점 높아짐)
1.2초  별이 하나씩 뿅 뿅 뿅
1.7초  경험치 바가 차오름 (레벨업하면 배지 등장)
2.1초  신기록이면 NEW RECORD 깜빡임
끝     버튼 3개가 또르르 등장
```

여기서 배운 것: **"몇 프레임 지났나"가 아니라 "몇 초 지났나"로 세야 한다**는 점이에요.
점수 카운트업을 "매 프레임 +1"로 만들면 기기가 버벅일 때 카운트업도 느려져요.
대신 "경과 시간 ÷ 0.8초 = 진행률"로 계산하면 버벅여도 정확히 0.8초에 끝납니다.

**Spring으로 비유하면**: 배치 작업을 "1000번 반복하면 끝"이 아니라
"마감 시각까지 진행률 기준으로" 설계하는 것과 같아요. 반복 횟수는 환경 따라 흔들리지만
시계는 안 흔들립니다.

## 2. 연출 중에 탭하면? — 스킵도 멱등이어야 한다

성격 급한 사람은 연출이 끝나길 안 기다려요. 화면을 탭하면 즉시 완성 상태로 점프합니다.

여기서 함정: 스킵이 **0.3초에 눌릴 수도, 1.5초에 눌릴 수도** 있어요.
도장만 찍힌 상태일 수도 있고, 별이 2개까지 나온 상태일 수도 있죠.
어느 타이밍에 눌러도 **결과는 똑같은 완성 화면**이어야 합니다.

해결 방법은 단순했어요. 스킵 함수가 6단계를 처음부터 끝까지 전부 다시 실행하되,
각 단계가 "이미 됐으면 건너뛰기" 가드를 갖게 했습니다. 두 번 실행돼도 안전한 거죠.

**Spring으로 비유하면**: 결제 재시도 API와 같은 멱등성 설계예요.
"이미 처리된 주문인지 확인 후 처리"를 모든 단계에 넣으면,
언제 끼어들어도·몇 번 불려도 최종 상태는 하나입니다.

덤으로, 버튼 3개는 연출이 끝나야 화면에 **추가**돼요. 숨겨놨다 보여주는 게 아니라
아예 없다가 생기는 거라, 연출 중에 버튼을 잘못 누르는 사고가 구조적으로 불가능합니다.

## 3. 별과 레벨은 저장하지 않는다 — 파생 값의 원칙

이번에 별점(★1~3)과 간호사 레벨(Lv.1~10) 시스템이 생겼는데,
**저장소에는 아무것도 새로 저장하지 않았어요.**

- 별 = 이미 저장 중인 "최고 점수"에서 그때그때 계산
- 레벨 = 이미 저장 중인 "누적 점수"에서 그때그때 계산

**Spring으로 비유하면**: DB에 `grade` 컬럼을 추가하는 대신
`총구매액 → 등급` 변환 메서드 하나만 두는 것과 같아요.
파생 값을 저장하면 원본과 어긋나는 순간(동기화 버그)이 반드시 오는데,
계산으로만 만들면 어긋날 데이터 자체가 없습니다. 정규화의 기본 원칙이죠.

## 4. 설계서대로 하면 앱이 못 켜진다? — 모순 게이트 발견

설계서에는 "★1 기준 점수가 게임의 목표 점수와 같은지 assert로 검사하라"고 적혀 있었어요.
그런데 설계서의 표는 60/50/30, 실제 코드의 목표 점수는 70/50/40.
**assert를 넣는 순간 개발 빌드가 부팅 즉시 크래시**합니다. 검사 자체가 모순이었던 거예요.

처리: 표 수치는 설계서대로 두되, assert 대신 **콘솔 경고 출력**으로 바꾸고
"숫자 맞추기 결정은 R6에서"라고 이관 기록을 남겼습니다. 몰래 덮은 게 아니라
QA 보고서에 "정당한 일탈"로 심사받고 통과했어요.

**Spring으로 비유하면**: 기획서의 검증 규칙대로 `@Validated`를 붙였더니
운영 DB의 기존 데이터가 전부 걸려서 서버가 못 뜨는 상황이에요.
이럴 때 검증을 몰래 빼면 안 되고, 경고 로그로 낮추고 데이터 정리 티켓을 발행하죠.
**규칙과 현실이 충돌하면, 충돌 사실을 기록으로 남기는 것까지가 일**입니다.

## 5. 팝업이 터치를 삼킨다 — 이벤트 가로채기 함정

계정 팝업을 새 PixelDialog 부품으로 갈아끼웠더니 위험한 함정이 하나 있었어요.
PixelDialog는 기본적으로 **자기가 터치를 받아 처리**하는 부품인데,
기존 계정 팝업은 **씬(화면)이 터치를 받아서** "어느 버튼 눌렸나"를 판정하는 구조였거든요.

그대로 조립하면 팝업이 터치를 먼저 삼켜버려서 씬까지 안 내려가요.
겉보기엔 멀쩡한데 **버튼이 하나도 안 눌리는** 화면이 됩니다.

해결: 팝업의 터치 수신 스위치를 꺼서(`isUserInteractionEnabled = false`)
터치가 씬까지 내려가게 했어요. 기존 판정 코드는 한 줄도 안 바꿨습니다.

**Spring으로 비유하면**: 새 라이브러리의 Servlet Filter가 요청을 먼저 가로채
기존 Controller까지 안 내려가는 상황이에요. 필터 체인 순서/등록을 조정해서
기존 진입점을 살리는 것과 같은 해법입니다. **새 부품을 끼울 땐 겉모양만 보지 말고
"입력(이벤트)이 누구한테 먼저 가는가"를 확인하라**는 교훈이에요.
