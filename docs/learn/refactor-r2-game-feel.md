# R2 학습 노트 — 게임필 (같은 게임인데 손맛이 다르다)

> 그랜드 리팩토링 v3의 세 번째 단계. R0가 "서랍 정리", R1이 "엔진 교체"였다면 R2는 **양념 단계**입니다. 기능은 하나도 안 늘었는데 때리는 맛·줍는 맛·죽는 맛이 달라지는, 게임 업계에서 "juice(즙)"라고 부르는 그것이요.

## 오늘 한 일 한 줄 요약

타격 순간 시간을 찰나만 멈추고(히트스톱), 카메라가 부드럽게 따라오며 흔들리고(카메라 v2), 파티클 6종이 터지고, 효과음 23개를 코드로 직접 합성하고(칩튠 신스), 진동을 정밀 설계하고(햅틱 v2), R1에서 미뤄둔 노드 수 숙제를 풀었습니다. 게임 규칙은 0줄 변경.

## 1. 히트스톱 — 만화책이 멋있는 이유

격투 만화에서 주먹이 꽂히는 컷은 **시간이 멈춰** 있습니다. 게임도 같은 트릭을 씁니다. F 폭탄에 맞는 순간 게임 세계를 0.1초만 얼리면(물리 정지 + 월드 일시정지), 뇌가 "방금 큰 일이 났구나"를 인지할 틈이 생겨요. 0.1초라 플레이어는 "멈췄다"가 아니라 "묵직하다"로 느낍니다.

재미있는 규칙 두 개:
- **겹치면 긴 쪽이 이긴다(longer-wins)**: 얼어 있는 중에 또 맞으면, 남은 정지 시간과 새 요청 중 긴 쪽만 남깁니다. 합산하면 시간이 누적돼 게임이 뚝뚝 끊겨요.
- **일시정지 메뉴가 열리면 즉시 취소**: "시간 멈춤"의 주인이 둘(히트스톱 vs 일시정지)이면 서로 풀어주다 꼬입니다. 메뉴 진입 시 히트스톱을 먼저 청소해 **시간의 주인을 한 명**으로 유지했습니다.

**Spring으로 치면**: 분산 락 갱신과 같습니다. 같은 키에 락 요청이 겹치면 TTL을 더하는 게 아니라 만료 시각을 `max(기존, 신규)`로 갱신하죠. 그리고 소유권이 다른 컨텍스트로 넘어갈 땐(일시정지) 기존 락을 명시적으로 해제하고 넘깁니다.

## 2. 카메라 v2 — 기록하는 손은 하나여야 한다

이번 단계의 설계 드라마입니다. 카메라에 세 가지 일이 동시에 걸립니다: 플레이어 **따라가기** + 피격 시 **흔들림** + 방향성 **킥**. 기존엔 흔들림이 SKAction(SpriteKit의 예약 애니메이션)으로 카메라 위치를 직접 건드렸는데, 따라가기 로직도 매 프레임 위치를 대입하니 **둘이 같은 변수를 두고 싸웠습니다**. 흔들림이 씹히거나 카메라가 순간이동하는 류의 버그가 여기서 나와요.

해법: `CameraDirector` 하나만 카메라 위치를 쓸 수 있게 했습니다. 따라가기·흔들림·킥은 각자 "희망값"만 내고, 매 프레임 디렉터가 셋을 합산해 **딱 한 번** 기록합니다. 흔들림용 SKAction은 삭제(파일째).

**Spring으로 치면**: 단일 기록자(single writer) 원칙. 두 서비스가 같은 테이블 행을 직접 UPDATE하면 레이스가 나니, 쓰기를 한 서비스로 모으고 나머지는 그 서비스에 요청만 보내는 구조죠.

덤: 따라가기 보간을 `1-exp(-8.5×dt)`로 바꿨습니다. 수식은 무서워 보이지만 뜻은 단순해요 — "남은 거리의 일정 비율씩 다가가되, **프레임 속도가 30이든 60이든 똑같은 빠르기로**". 고정 비율(매 프레임 10%씩)은 60fps 기기에서 두 배 빨리 따라붙는 버그가 됩니다.

## 3. 파티클 6종 — 불꽃놀이에도 정원이 있다

음표 수집 반짝, 콤보 오라, 사망 폭발, 스킬 시그니처, 변기 물튀김, 마일스톤 색종이 — 6종을 전부 **코드로** 만들었습니다(.sks 파일 0개, 설정값은 전부 Config 상수라 리뷰·튜닝이 diff로 보입니다).

핵심은 만들기보다 **제한**입니다. 동시 이미터 8개 캡 + 우선순위(사망 폭발 > 스킬 > ... > 콤보 오라). 9번째가 오면 제일 안 중요한 걸 퇴거시키거나 신규를 거절합니다. 연출은 양념인데 양념이 프레임을 떨어뜨리면 본말전도니까요.

**Spring으로 치면**: 스레드 풀 + 우선순위 큐 + 거절 정책(RejectedExecutionHandler)입니다. 풀 크기를 안 정하면 트래픽 몰릴 때 서버가 죽는 것처럼, 이미터도 캡 없이 쓰면 보스 러시 순간에 프레임이 죽습니다.

## 4. ChiptuneSynth — 효과음 파일 0개로 효과음 23개

효과음을 mp3로 넣는 대신 **수학으로 만들었습니다**. 옛날 게임기 소리(칩튠)는 사각파·삼각파·톱니파 같은 단순 파형이라 코드 몇 줄로 합성이 가능해요. 음표를 먹을수록 도→도#→레… 반음씩 올라가는 13단 음계도 이걸로 공짜.

단, 게임 도중 합성하면 그 계산이 프레임을 갉아먹습니다. 그래서 **시작할 때 23개 버퍼를 전부 미리 렌더**해두고, 게임 중에는 재생 버튼만 누릅니다. 런타임 합성 0회.

**Spring으로 치면**: `@PostConstruct` 캐시 워밍입니다. 첫 요청이 느린 게 싫으면 부팅 때 미리 구워두라 — 그 원칙 그대로요. 구형 `AudioServicesPlaySystemSound`(시스템 효과음)는 전폐하고 AudioManager 파일도 삭제했습니다.

## 5. R1 숙제 풀기 — "연출을 바꿀 수 없다"면 연출을 다시 설계하면 된다

R1 노트의 드라마를 기억하나요? hard 난이도 노드 수가 368로 게이트(≤300)를 넘겼는데, 원인인 F 폭탄·청진기의 빛 테두리 자식 노드 2개가 "스칠 때 번쩍이는 연출"을 갖고 있어 **행동 불변 원칙상 R1에서는 합칠 수 없었습니다**. 그래서 "연출 재설계가 허용되는 R2로 이관"으로 기록했었죠.

R2에서 푼 방법: 본체+테두리+빛을 그림 한 장으로 굽되(베이크), **"보통 모습"과 "번쩍이는 모습" 두 장**을 구워서 번쩍일 타이밍에 그림을 교차(setTexture)합니다. 자식 노드의 크기 애니메이션 → 텍스처 2장 교차로 연출 수단만 바뀌고, 깜빡이는 주기 상수는 기존 값 그대로. 결과: 폭탄 1발이 3노드 → 1노드, hard 평시 **≈270으로 게이트 재충족**. 물리 판정 크기는 byte 단위로 동일하게 보존했습니다(맞는 범위가 달라지면 게임성이 바뀌니까).

**교훈**: "할 수 없다"는 대부분 "이 제약 아래서는"이라는 조건부입니다. 제약이 풀리는 단계로 기록과 함께 이관했더니, 거기선 자연스럽게 풀렸어요. 이관 기록이 없었다면 영원히 368이었을 겁니다.

## 6. QA 드라마 — "했다"는 주장은 증거가 아니다

이번 사이클의 백미. 구현 담당(generator)이 자가 점검표에 "마일스톤 색종이 배선 완료"라고 썼는데, 검수 담당(evaluator)이 믿지 않고 `grep`으로 호출처를 전수 추적하니 **호출 0건** — 색종이를 만들어놓고 터뜨리는 코드를 안 꽂은 거죠. 만들기만 한 폭죽은 영원히 안 터집니다. P1로 적발 → 2줄 수정 → 재검수 통과(8.65 → 9.45).

**Spring으로 치면**: "로컬에서 테스트 통과했어요"를 믿지 않고 CI가 직접 빌드·테스트를 돌리는 이유입니다. 자가 보고는 검증의 **대상**이지 증거가 아니에요. 우리 하네스가 generator와 evaluator를 **반드시 다른 에이전트**로 분리하는 것도 같은 이유 — 자기가 만든 걸 자기가 채점하면 이런 게 통과됩니다.

## 오늘의 핵심 교훈

1. **게임필은 기능이 아니라 타이밍이다** — 0.045초의 멈춤, 0.9초의 지연(게임오버 연출이 보인 뒤 결과 화면). 숫자는 작지만 전부 상수로 박아 튜닝 가능하게.
2. **같은 변수를 쓰는 손은 하나로** — 카메라 위치의 단일 기록 지점. 경합은 합산이 아니라 구조로 푼다.
3. **연출 예산도 예산이다** — 이미터 캡 8 + 우선순위 퇴거. 제한 없는 양념은 본체를 죽인다.
4. **자가 보고는 검증하라** — "배선했다"는 grep 한 줄이면 확인된다. 분리된 검수가 허위를 잡는다.
