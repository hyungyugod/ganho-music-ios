# 학습 노트 — 리팩토링 R8: 통합 QA·릴리즈 준비 + 캐릭터 일러스트 카드 (2026-06-11)

> 이번에 한 일: v3 리팩토링의 마지막 단계였습니다.
> 창고에서 잠자던 옛 캐릭터 일러스트 5장을 꺼내 캐릭터 선택창에 다시 걸었고(빛나는
> 받침판과 둥실둥실 떠 있는 효과로 지금 UI에 녹였습니다), 콤보 숫자가 "0"에 붙어버리는
> 오래된 버그를 1줄로 고치고, "아슬!" 판정의 잣대 자체를 바꾸고, 일시정지 메뉴를
> 새 디자인으로 바꾸고, 출하 전 대청소(금지 패턴 검사·안 쓰는 상수 60개 처분·문서 3종)를
> 마쳤습니다. R0~R8 전 단계 합격 — 리팩토링 끝.

## 1. 창고의 자산을 꺼낼 때는 "없으면 어쩔 건데"부터 정한다

옛날에 쓰던 캐릭터 일러스트 5장이 자산 카탈로그(Assets.xcassets) 안에
**아무도 안 부르는 채로** 들어 있었어요. 파일은 앱에 이미 실려 다니는데
코드에서 참조가 0건 — 창고에 쌓인 재고였던 거죠.

이걸 다시 쓸 때 제일 먼저 정한 건 그림 배치가 아니라 **실패 시나리오**였습니다.
"이름으로 이미지를 불렀는데 없으면?" — 강제로 꺼내다 터뜨리는 대신,
없으면 기존 픽셀 초상화로 **조용히 대체**하게 했어요:

```swift
guard let image = UIImage(named: name) else {
    return PixelPortraitSprite.texture(for: id)   // 없으면 옛날 방식으로
}
```

**Spring으로 비유하면**: `@ConditionalOnMissingBean`이나 폴백 Bean이에요.
외부 리소스를 믿고 `get()`으로 터뜨리는 코드 대신, "없으면 기본 구현"을
미리 꽂아두는 것. 리소스 하나 빠졌다고 앱이 죽으면 안 되니까요.

## 2. 안 어울리는 두 스타일은 "변환"이 아니라 "포장"으로 섞는다

문제: 일러스트는 부드러운 곡선 그림인데, 지금 UI는 각진 픽셀 아트예요.
그냥 올려놓으면 다른 게임에서 온 손님처럼 붕 뜹니다.

일러스트를 픽셀화(변환)하는 길도 있지만, 잘 뽑힌 원본을 망가뜨리는 짓이죠.
대신 **원본은 그대로 두고, 주변을 지금 UI의 시각 언어로 포장**했습니다:

- **시그니처 받침판**: 캐릭터마다 정해진 고유색(이미 게임 전체가 쓰는
  `Palette.character`)을 일러스트 뒤에 은은하게(투명도 0.22) 깔았어요.
  "이 그림도 우리 식구"라는 도장입니다.
- **둥실 모션**: 선택된 카드의 일러스트만 0.9초에 ±3pt씩 떠 있게 — 살아있는
  느낌은 픽셀이든 일러스트든 통하는 공용어예요.
- **확대 필터만 구분**: 픽셀 그림은 `.nearest`(또렷한 계단), 일러스트는
  `.linear`(부드러운 보간) — 자산 종류마다 맞는 확대 방식을 **명시**했습니다.

**Spring으로 비유하면**: 외부 API의 응답 DTO를 우리 도메인 객체로 변환하지 않고
그대로 쓰되, **어댑터로 감싸서** 우리 인터페이스를 입히는 거예요. 원본 데이터는
손대지 않고, 우리 시스템의 "언어"는 지키는 절충.

덤: 카드 부품(PixelCharacterCardNode)은 캐릭터 선택창과 스킬 설명창이
**공유**해요. 한 군데 고쳤더니 두 화면이 같이 바뀌었습니다. 공용 Bean의
양날 — 편하지만, 고칠 때 "이거 어디어디서 쓰지?"를 반드시 먼저 세어야 합니다.

## 3. 캐시만 갱신하고 화면을 안 고치면, 영원히 안 고쳐진다

콤보 숫자 칩이 게임 내내 "0"에 붙어 있는 버그가 있었어요. 범인은 이 패턴:

```
펄스 연출 함수: lastDisplayedCombo = combo   // "표시했다"고 메모만 하고
                (실제 화면 글자는 안 바꿈!)    // 화면은 안 바꿈
매 프레임 갱신: combo != lastDisplayedCombo 일 때만 화면 갱신
                → 메모가 항상 "이미 표시함"이라 영원히 건너뜀
```

"이미 그렸다"는 **메모(캐시)**와 **실제 화면**이 어긋난 채 고정된 거예요.
고치는 건 1줄 — 메모할 때 화면도 같이 바꾸면 됩니다.

**Spring으로 비유하면**: DB는 업데이트했는데 `@CacheEvict`를 빼먹은 상황의
정반대 버전이에요. 캐시에는 "새 값 반영됨"이라고 적어놓고 정작 DB(화면)는
안 건드린 것. 캐시와 원본은 **한 트랜잭션처럼 같이** 움직여야 합니다.
1줄짜리 수정이지만, 원인 설명 주석을 같이 남겨서 다음 사람이 같은 함정을
파지 않게 했어요.

## 4. 수치를 키우지 말고, 잣대가 틀렸으면 잣대를 바꿔라

"아슬!"(near-miss) 보상이 5판 내내 한 번도 안 터졌어요. 판정은
"투사체 **중심**과 플레이어 **중심**이 22px 이내"였는데, 기하학을 따져보니:

- 플레이어는 점이 아니라 16×20 상자, 투사체도 16×16 상자예요.
- 대각선으로 스치면 **중심끼리 24px 떨어져도 이미 충돌**합니다.
  즉 대각 궤적은 "아슬 판정 반경에 들어오기 전에 맞아버림" — 발동이
  **수학적으로 불가능**한 사각지대였어요.

반경을 22→26px로 키우는 안도 있었지만, 그래 봤자 대각 통과 대역은 2px쯤.
근본 문제는 숫자가 아니라 **"중심 거리"라는 잣대 자체**였습니다. 그래서
"두 상자의 **가장자리** 사이가 10px 이내"로 기준을 바꿨어요(상자끼리의
거리는, 한쪽 상자를 상대 크기만큼 부풀린 뒤 점-상자 거리로 재는 표준
기법으로 — 추가 메모리 0). 결과: 5판에 7회 발동.

**Spring으로 비유하면**: 평균 응답시간만 보다가 장애를 놓치는 것과 같아요.
평균(중심 거리)이라는 지표가 구조적으로 못 보는 영역(대각 궤적·p99)이
있으면, 임계값을 조정할 게 아니라 **지표를 바꿔야** 합니다. 그리고 잣대를
바꿨으면 설계 문서도 그 자리에서 같이 고쳐야 해요(02_GAME_FEEL 동반 갱신) —
코드와 문서가 다른 잣대를 말하는 순간부터 다음 작업자가 헤맵니다.

## 5. 민감한 절차는 그대로 두고, 껍데기만 갈아 끼운다

일시정지 메뉴를 새 디자인(v3 다이얼로그)으로 바꿨는데, 여기서 진짜 무서운 건
버튼 모양이 아니라 **동결/복원 절차**예요. 일시정지는
"히트스톱 취소 → 입력 리셋 → 터치 차단 → 물리 정지 → 속도 0"을
정확한 순서로 밟고, 해제는 역순으로 밟아야 합니다. 한 줄만 순서가 틀려도
"해제했는데 캐릭터가 안 움직임" 같은 유령 버그가 나와요.

그래서 이번 교체는 **절차 코드는 1바이트도 안 건드리고**, 그 위에 얹히는
오버레이(보이는 부분)만 새 부품으로 갈았습니다. 검수도 "절차 부분 diff가
0인가"로 했고요.

**Spring으로 비유하면**: 트랜잭션 경계와 락 순서가 박힌 서비스 레이어는
그대로 두고 컨트롤러/뷰만 교체하는 거예요. 리팩토링의 안전벨트는
"무엇을 바꿨나"보다 **"무엇을 안 바꿨다고 증명할 수 있나"**입니다.

## 6. 출하 전 대청소 — 삭제는 "참조 0 증명"이 먼저다

릴리즈 준비의 반은 청소였어요. 안 쓰는 색·좌표·연출 상수 약 60종을 지웠는데,
규칙은 하나: **지우기 전에 "아무도 안 쓴다"를 grep으로 증명**하고, 지운 자리에
"언제 왜 지웠는지" 묘비 주석을 남긴다. 실제로 증명 단계에서 "안 쓰는 줄
알았던" 상수 2개가 현역으로 밝혀져 살아남았습니다 — 감이 아니라 검색이
판정합니다.

300줄 넘는 파일 5개도 쪼갰는데(최대 625줄 → 전부 300 이하), 핵심은
**코드를 고치지 않고 옮기기만** 한다는 것. 옮긴 코드가 원본과 byte 단위로
같은지 표본 대조로 검수했어요. Spring의 패키지 재구성과 같습니다 —
이사와 리모델링을 같은 날 하면, 문제가 생겼을 때 원인이 이사인지
리모델링인지 알 수 없게 돼요.

마지막으로 금지 패턴 전수 검사(강제 언래핑·Timer·매직넘버 등 — 전부 0건),
12개 화면 노드 수 실측표(전부 예산 안), 스크린샷 13장, 디버그 플래그 문서,
최종 감사 보고서(refactor/R8_FINAL_AUDIT.md)까지. **출하 게이트는 사람의
기억이 아니라 체크리스트와 grep이 통과시킵니다.**
