# 학습 노트 — 리팩토링 R4: 메뉴 씬 재구축 (2026-06-10)

> 이번에 한 일: 게임의 메뉴 화면 4개(시작·캐릭터 선택·스킬 설명·난이도 선택)를
> 새 픽셀 디자인("Night Shift")으로 완전히 새로 만들었습니다.
> 옛날 디자인 부품 11개는 쓰레기통으로 보냈습니다.

## 1. "화면만 갈아끼우고 속은 그대로" — 뷰 교체

이번 작업의 가장 중요한 원칙은 **보이는 것만 바꾸고, 동작은 1도 안 바꾼다**였어요.

- 로그인 처리, 캐릭터 잠금 해제 조건, 난이도별 목표 점수 같은 "속 로직"은 그대로
- 화면에 그려지는 버튼·카드·글씨체만 전부 새것으로

**Spring으로 비유하면**: JSP로 만든 화면을 Thymeleaf로 갈아끼우는 작업이에요.
Controller와 Service는 한 줄도 안 건드리고 템플릿 파일만 전부 새로 쓰는 거죠.
화면이 완전히 달라 보여도 "회원가입 버튼을 누르면 일어나는 일"은 똑같습니다.

이게 가능했던 이유는 R3에서 미리 **부품(컴포넌트)을 만들어 뒀기 때문**이에요.
PixelButton, PixelCard, PixelDialog 같은 부품을 조립만 하면 화면이 완성됩니다.
Spring에서 공통 레이아웃 fragment를 미리 만들어 두고 페이지마다 갖다 쓰는 것과 같아요.

## 2. 버튼 연타 방지 — `isTransitioning` 가드

QA에서 잡힌 버그 하나가 좋은 교훈이었어요.

**문제**: 화면이 넘어가는 0.35초 동안 다른 버튼을 또 누르면?
화면 전환이 **두 번** 시작돼서 게임이 이상해질 수 있었어요.
(두 손가락으로 버튼 두 개를 동시에 누르면 실제로 터집니다)

**해결**: "지금 화면 넘어가는 중"이라는 깃발(`isTransitioning`)을 세우고,
깃발이 올라가 있으면 모든 버튼 입력을 무시합니다.

```swift
guard !isTransitioning, let view = self.view else { return }
isTransitioning = true   // 깃발 올리기 — 이제 다른 터치는 무시됨
```

**Spring으로 비유하면**: 결제 버튼 더블 클릭 방지와 똑같은 패턴이에요.
주문 처리 중에 또 주문 요청이 들어오면 거절하는 것 —
멱등성(idempotency) 보장의 가장 단순한 형태입니다.

교훈: **"넘어가는 중"이라는 상태도 상태다.** 화면 전환처럼 시간이 걸리는 일은
시작할 때 잠그고, 끝나거나 취소될 때 풀어주는 관리가 필요해요.

## 3. 컴파일러가 죽는 버그 — `@inline(never)` 우회 (선행 픽스)

R4 시작 전에 이상한 문제를 하나 풀었어요. **앱이 아니라 컴파일러가 죽는** 버그였습니다.

- Debug 빌드(개발용)는 멀쩡한데 Release 빌드(출시용)만 실패
- 원인: 출시용 빌드는 코드를 빠르게 만들려고 "최적화"를 하는데,
  그 최적화 도구가 우리 ObjectPool 코드를 분석하다가 자기가 뻗어버림

**해결**: 코드에 "이 부분은 최적화로 합쳐넣지 마"라는 표시(`@inline(never)`)를 한 줄 붙여서
컴파일러가 문제의 분석 자체를 건너뛰게 했어요. 동작은 그대로, 컴파일러만 달램.

**Spring으로 비유하면**: JVM의 JIT 컴파일러 버그를 만났을 때
특정 메서드만 JIT 제외 옵션을 거는 것과 비슷해요. 내 코드가 틀린 게 아니라
도구의 버그를 우회하는 거라서, "왜 이 표시가 붙어있는지" 주석을 꼭 남겨야 합니다.

## 4. 파일이 너무 길어지면 쪼갠다 — extension 분할

캐릭터 선택 화면은 할 일이 많아요 (카드 배치, 계정 메뉴, 오버레이...).
한 파일에 다 넣으면 700줄짜리 괴물이 됩니다. 이 프로젝트 규칙은 **한 파일 300줄 이하**.

그래서 Swift의 `extension` 기능으로 역할별로 4개 파일로 쪼갰어요:

```
CharacterSelectScene.swift           ← 본체 (상태와 핵심 흐름)
CharacterSelectScene+Layout.swift    ← 화면 배치만
CharacterSelectScene+Overlays.swift  ← 팝업들만
CharacterSelectScene+Account.swift   ← 계정 관련만
```

**Spring으로 비유하면**: 하나의 Service가 비대해지면 역할별로 나누는 것과 같은데,
Swift의 extension은 **클래스는 하나인데 파일만 나뉘는** 점이 달라요.
자바에는 없는 기능이라 처음엔 낯선데, "같은 클래스의 챕터 나누기"라고 생각하면 됩니다.

## 5. QA가 두 번 돈 이유 — 합격점이어도 P1은 못 넘어간다

1회차 QA 점수는 8.6으로 합격선(7.5)을 넘었어요. 그런데도 한 번 더 돌았습니다.
**P1(중요 버그) 2건이 발견됐기 때문** — 위의 버튼 연타 버그가 그중 하나예요.

점수가 합격이어도 알려진 버그를 안고 다음 단계로 가면,
다음 단계에서 그 버그가 어디서 터졌는지 찾기가 훨씬 어려워져요.
**버그는 발견된 그 자리에서 잡는 게 제일 싸다**는 원칙입니다.

**Spring으로 비유하면**: 테스트 커버리지가 기준을 넘어도
Critical 등급 SonarQube 이슈가 있으면 머지를 막는 브랜치 보호 규칙과 같아요.
