# 닉네임 창 진짜 작동하게 + 결과창 BEST 위치 정리

## 한 줄로

**"저장 버튼은 멀쩡했는데, 키보드가 그 위를 덮고 있어서 못 누른 것"** 이다. 키보드가 올라오면 입력창 전체를 위로 살짝 들어올려 저장 버튼이 항상 보이게 했고, 키보드의 체크(✓)만 눌러도 저장되게 연결했다. 입력칸도 헷갈리는 2개에서 닉네임 1개로 줄였다. 덤으로 결과창에서 점수 "0" 바로 밑에 끼어 있던 BEST 알약을 아래로 충분히 내려 숨통을 틔웠다.

## 무슨 문제였나 (스크린샷 2장)

1. **닉네임 창**: 닉네임을 적어도 "저장"이 안 눌리고, 입력칸이 왜 2개인지 모르겠다.
2. **결과창**: "BEST 78" 알약 위치가 이상하다(점수에 딱 붙어 끼어 있음).

## 문제 1 — 닉네임 창, 원인이 3개였다

### (1) 입력칸이 2개였던 이유

창 제목은 "닉네임 설정"인데, 안에는 칸이 **2개**였어.

- `displayNameField` = **표시이름** (Apple 로그인에서 받아오는 진짜 이름)
- `nicknameField` = **닉네임** (게임 안에서 불릴 별명)

둘 다 비슷하게 생겨서 "닉네임 칸이 왜 두 개야?" 싶었던 거지. 제목이 "닉네임 설정"이니까 **닉네임 칸 하나만** 남기고 표시이름 칸은 없앴어.

> ⚠️ 그런데 그냥 지우면 Apple에서 받아온 표시이름 데이터가 날아가. 그래서 **저장할 때 기존 표시이름 값을 손대지 않고 그대로 같이 넘겨**주도록 했어. 화면에서만 안 보이고, 데이터는 보존되는 거야.
>
> **Spring 비유**: DTO에 `name`, `nickname` 두 필드가 있는데 수정 폼에서는 `nickname`만 보여주고 싶을 때, `name`은 화면에 안 띄우되 `@RequestBody`로 받을 때 **기존 값을 그대로 다시 넣어서(hidden 필드처럼)** UPDATE 치는 것과 똑같아. 필드를 DB에서 지운 게 아니라, 입력 폼에서만 뺀 거지.

### (2) 저장 버튼을 못 누른 진짜 이유 — 키보드가 덮고 있었다

이게 핵심이야. **저장 버튼은 고장 안 났어.** 버튼이 화면 가운데 창의 아래쪽에 있는데, 가로 모드에서 키보드가 올라오면 키보드가 화면 아래 절반을 꽉 채워서 **저장 버튼이 키보드 뒤로 숨어버린** 거야. 손가락이 닿는 곳은 키보드지 버튼이 아니었던 거지.

해결: **키보드가 올라오는 걸 감지해서, 입력창 전체를 그만큼 위로 들어올렸어.** 키보드가 내려가면 다시 제자리로.

비유하자면, 책상 위에 서류(입력창)가 있는데 큰 상자(키보드)가 책상 절반을 덮으면 서류 아랫부분이 안 보이잖아. 그럼 서류를 위로 쓱 올려서 상자 위로 빼주는 거야.

> **Spring 비유**: 이건 백엔드엔 없는 **프론트(클라이언트) 고유의 골칫거리**야. 굳이 비유하면, 응답이 화면 영역을 벗어나지 않게 **레이아웃을 동적으로 조정**하는 거라, 서버에서 페이지 크기에 맞춰 결과를 잘라주는(pagination) 느낌과 비슷해. "보이는 영역"이라는 제약에 맞춰 위치를 다시 계산하는 거지.

### (3) 키보드의 체크(✓)키가 먹통이었다

키보드 오른쪽 파란 체크키(완료키)를 눌러도 **아무 일도 안 일어났어.** 키 모양만 "완료"로 바꿔놨지, "완료를 누르면 뭘 해라"를 안 정해놨던 거야.

그래서 **체크키 = 저장**으로 연결했어. 칸이 하나니까 다 적고 체크 누르면 바로 저장되는 게 자연스럽지.

> **Spring 비유**: 컨트롤러에 `@PostMapping`만 써놓고 메서드 본문을 비워둔 거랑 같아. URL(완료키)은 있는데 핸들러가 없으니 눌러도 무반응. 핸들러(`textFieldShouldReturn` → 저장)를 채워준 거야.

### 멱등성(idempotent) — 같은 걸 두 번 해도 결과가 같아야 한다

키보드를 올릴 때 작은 함정이 하나 있었어. 키보드가 뜰 때 iOS는 신호를 **한 번이 아니라 여러 번** 보내(처음 뜰 때 + 한글 후보 글자 막대가 생길 때 등). 그런데 "지금 창 위치"를 기준으로 "얼마나 올릴지"를 계산하면:

- 1번째 신호: 창이 가운데 있음 → "100만큼 올려" → 올림
- 2번째 신호: 창이 이미 100 올라가 있음 → "어, 이제 안 겹치네 → 0으로 내려" → **도로 떨어져서 또 가려짐** 😱

그래서 계산을 **항상 "원래(안 올린) 위치" 기준**으로 하도록 고쳤어(`이미 올린 양`을 빼고 계산). 그러면 신호가 몇 번 오든 결과가 똑같아져 — 이게 **멱등성**이야.

> **Spring 비유**: 멱등성은 백엔드 단골 개념이지! `PUT /user/1 {age:20}`은 100번 호출해도 결과가 age=20으로 똑같지만, `POST .../age/increment`는 부를 때마다 +1 돼서 위험하잖아. 키보드 올리기를 "현재값 +이동"(increment)으로 짰다가 버그가 났고, "원래값 기준 절대값"(PUT처럼)으로 바꿔 고친 거야.

## 문제 2 — 결과창 BEST 알약이 점수에 끼어 있었다

결과창 왼쪽은 위에서부터 **헤더칩 → 제목("실습 종료") → 큰 점수("♪ 0") → BEST 알약** 순서로 쌓여.

원래 코드는 BEST 알약을 "점수 중심에서 48만큼 아래"에 뒀는데, 점수 글자가 워낙 커서(64pt) **점수 글자 아랫부분과 알약이 거의 맞닿아** 있었어(빈틈 2pt). 그래서 끼어 보인 거야.

고친 방법: 단순히 "점수 중심에서 얼마"가 아니라, **"점수 글자의 실제 아랫변에서 + 넉넉한 간격(40) + 알약 절반 높이"** 로 계산했어. 이제 점수와 알약 사이에 시원하게 40pt 숨통이 생겼지.

> 단, 화면이 아주 낮은 기기에선 알약을 너무 내리면 아래 PLAYS/TOTAL 글자랑 부딪혀. 그래서 **"점수 밑 넉넉히"와 "아래 통계랑 최소 간격" 중 더 안전한 쪽을 자동으로 고르게**(`max`) 했어. 넓으면 시원하게, 좁으면 부딪히기 직전까지만.

비유하면, 엘리베이터에 사람을 태울 때 "앞사람과 한 걸음 띄우기"가 기본인데, 칸이 좁으면 "벽에 닿기 직전까지만" 물러서는 것과 같아. 둘 중 안전한 쪽을 그때그때 고르는 거지.

## 좌표 방향 함정 — 위로 가려면 부호가 반대다

이번 작업은 **두 개의 다른 좌표계**를 동시에 만져서 헷갈리기 쉬웠어.

| | 원점(0,0) 위치 | "위로" 가려면 |
|---|---|---|
| **UIKit** (닉네임 창) | 왼쪽 **위** | Y를 **빼기**(음수) |
| **SpriteKit** (결과창) | 왼쪽 **아래** | Y를 **더하기**(양수). 점수 아래로 두려면 Y를 빼기 |

같은 "위로 올려"라는 말이 한쪽은 `-`, 한쪽은 결과가 반대야. 수학 시간의 그래프(y는 위로 갈수록 큼)는 SpriteKit 쪽이고, 화면 픽셀(맨 위가 0줄)은 UIKit 쪽이라고 생각하면 외우기 쉬워.

## 어떻게 작업했나 (하네스)

이 프로젝트 규칙대로 **설계자(Planner) → 구현자(Generator) → 검수자(Evaluator)** 3명이 차례로 일했어.

- **설계자**: 원인 3개를 SPEC 문서로 정리
- **구현자**: 코드 수정 + 빌드 성공 확인
- **검수자**: SPEC대로 됐는지 채점 → **합격 9.1/10**

중간에 내가(오케스트레이터) 키보드 멱등성 버그를 직접 한 번 더 잡았고.

> **Spring 비유**: 기획서(SPEC) → 개발(Generator) → 코드리뷰(Evaluator) 파이프라인이야. CI에서 빌드 깨지면 머지 안 되는 것처럼, 빌드 성공 + 리뷰 통과를 합격 조건으로 박아둔 거지.
