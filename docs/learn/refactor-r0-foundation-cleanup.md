# R0 학습 노트 — 기반 정리 (행동 불변 리팩토링)

> 그랜드 리팩토링 v3의 첫 단계. **게임은 1픽셀도 안 바뀌었는데 코드는 완전히 새 집이 된** 작업입니다.

## 오늘 한 일 한 줄 요약

3,869줄짜리 "만능 설정 파일" 하나를 도메인별 7개 파일로 쪼개고, 옛날 버전 흔적 309개를 지우고, 아무도 안 쓰는 코드를 삭제했습니다. 게임 동작은 그대로입니다.

## 1. god-config 해체 — 서랍 정리 비유

**전**: `GameConfig.swift` 한 파일에 이동 속도, 버튼 색깔, 저장 키, 폰트 크기… 전부 다 들어 있었습니다(3,869줄). 집안 물건 전부를 거실 한가운데 큰 상자 하나에 던져 넣은 상태예요. 뭘 찾으려면 상자를 다 뒤져야 하죠.

**후**: 성격별로 서랍을 나눴습니다.

| 새 파일 | 들어간 것 | 비유 |
|---|---|---|
| `GameplayTuning` | 이동 속도·스폰 간격·스킬 쿨다운 | 게임 규칙 서랍 |
| `FeelTuning` | 화면 흔들림·연출 시간 | 손맛 서랍 |
| `UILayout` | 패널 폭·여백·버튼 크기 | 가구 배치도 |
| `Typography` | 폰트 이름·글자 크기 | 글씨체 서랍 |
| `ZOrder` | 화면 위아래 겹침 순서 | 종이 쌓는 순서표 |
| `StorageKeys` | 저장소 키 문자열 | 금고 열쇠 꾸러미 |

**Spring으로 치면**: `application.properties` 하나에 DB 설정·보안 설정·로깅 설정을 전부 몰아넣다가, `@ConfigurationProperties(prefix = "db")` 처럼 도메인별 설정 클래스로 분리한 것과 똑같습니다. 호출하는 쪽도 `GameConfig.enemySpeed` 대신 `GameplayTuning.enemySpeed`라고 쓰니까 "아, 이건 게임 규칙 수치구나"가 이름만 봐도 읽힙니다.

**중요한 규칙 하나**: 옛 이름을 살려주는 "다리"(typealias)를 일부러 안 만들었습니다. 111개 파일의 호출부를 전부 새 이름으로 고쳤어요. 다리를 남기면 편하지만, 반쯤 이사한 집처럼 옛 주소와 새 주소가 영원히 공존하게 됩니다. Spring에서 `@Deprecated` 메서드를 안 지우고 10년 묵히는 것과 같은 일이죠.

## 2. 버전 suffix 박멸 — "최종_진짜최종_v12.hwp" 청소

코드에 `resultPanelHeightV12`, `skillButtonZPositionV4` 같은 상수가 309개 있었습니다. 과거에 디자인을 바꿀 때마다 옛 값을 지우지 않고 V2, V3… 새 이름을 만들어온 흔적이에요. 과제 폴더의 "최종.hwp, 진짜최종.hwp, 이게_진짜최종_v12.hwp"와 같은 상태입니다.

정리 규칙은 단순합니다:
- 실제로 쓰이는 최신값만 남기고 → suffix를 떼서 본래 이름으로 (`V12` → 그냥 `resultPanelHeight`)
- 아무도 안 부르는 옛 버전 157개 → 삭제

"옛 값이 필요해지면 어떡해?"라는 걱정은 git이 해결합니다. 모든 과거 값은 커밋 기록에 영원히 남아 있으니까요. **버전 관리는 이름이 아니라 git이 하는 것** — 이게 오늘의 핵심 교훈입니다.

## 3. dead code 삭제 — 아무도 안 누르는 버튼 떼기

"호출하는 곳이 0군데"인 코드를 찾아 지웠습니다. 파일 2개(`CharacterFullBodyNode`, `GradientBackgroundNode`), 안 쓰는 색 토큰 27개 등.

특히 **좀비 노드** 7개가 재미있는 사례였어요. 결과 화면에 라벨 7개를 만들어 붙여놓고 `alpha = 0`(투명도 0)으로 숨겨만 둔 코드였습니다. 화면에 안 보이지만 메모리에 살아 있고, 코드 읽는 사람은 "이거 언젠가 쓰이나?" 하고 계속 신경 쓰게 되죠. 무대 뒤에 마네킹을 세워두고 막을 안 올리는 격입니다. 전부 삭제했습니다.

단, `baseSpeedEnd` 하나는 **일부러 남겼습니다**. 지금은 안 쓰지만 R2 단계에서 "플레이어 속도 곡선" 기능에 쓸 예정이라 설계서에 "삭제 금지"로 명시돼 있었거든요. 삭제/보존 판단은 느낌이 아니라 **설계서와 호출처 검색 결과**로 합니다.

## 4. 중복 4벌 → 프로토콜 1벌

플레이어, 적, 교수님, 석상 — 4개 캐릭터 노드에 "4방향 바라보기 + 걷기 애니메이션" 코드가 거의 똑같이 복사-붙여넣기 되어 있었습니다. 한 군데 버그를 고치면 나머지 3곳도 따라 고쳐야 하는 구조죠.

이걸 `PixelCharacterAnimating`이라는 **프로토콜**(Swift의 인터페이스)로 추출했습니다. 공통 동작은 프로토콜 확장(extension)에 한 번만 쓰고, 4개 노드는 "나도 그 능력 채택할게"라고 선언만 합니다.

**Spring으로 치면**: 서비스 4개에 복붙된 공통 로직을 인터페이스의 `default` 메서드(혹은 추상 클래스)로 끌어올린 것입니다. Swift의 "프로토콜 + extension"은 자바 인터페이스의 default 메서드와 거의 같은 개념이에요.

## 5. 절대 건드리면 안 됐던 것 (P0 불변 조건)

리팩토링에서 제일 중요한 건 "뭘 바꿨나"보다 "**뭘 안 바꿨나**"입니다.

- **저장소 키 문자열**: `StorageKeys.swift`로 위치는 옮겼지만 문자열 값은 한 글자도 안 바꿈. 키가 바뀌면 기존 유저의 최고기록이 전부 증발합니다. Spring으로 치면 DB 컬럼명을 바꾸면서 마이그레이션을 안 한 것과 같은 사고예요.
- **픽셀 데이터**: 캐릭터 도트 그림 데이터는 git diff 0줄 (byte 단위로 동일).
- **상수 값**: 1,600여 개 상수를 옮기면서 **값은 전부 그대로**. QA에서 옛 파일과 새 파일의 값을 기계적으로 전수 비교해 "라이브 상수 변경 0건"을 증명했습니다.

## 오늘의 핵심 교훈

1. **행동 불변 리팩토링은 "증명"이 절반** — "안 바뀌었을 거야"가 아니라 grep 0건, diff 0줄, 값 전수 대조로 증명한다.
2. **과거 보관은 git의 일** — V4, V12 같은 이름이나 alpha=0 숨김으로 과거를 코드에 남기지 않는다.
3. **다리(typealias)를 놓지 말고 이사를 끝내라** — 과도기 호환층은 영원히 남는다.
