## 1. 1회용 티켓을 두 번 내면 거절당한다 — 그런데 거절문 안에 새 티켓이 들어 있다

Apple 로그인이 "잠시 후 다시 시도해 주세요"로 튕기던 진짜 원인:

1. 우리 앱은 시작할 때 항상 **익명 계정**을 먼저 만들어 둡니다.
2. 그래서 Apple 로그인을 하면 "익명 계정에 Apple을 **연결**(link)"부터 시도해요.
3. 그런데 그 Apple ID가 **예전에 다른 계정에 이미 연결**돼 있었다면? 연결은 실패합니다.
4. 여기서 함정 — 실패했으니 "그럼 그냥 로그인(signIn)으로 다시 시도"를 했는데,
   **같은 Apple 토큰을 그대로** 다시 썼어요. Apple 토큰은 **1회용 입장권**이라
   연결 시도 때 이미 사용 처리됐고, 두 번째 제출은 "이미 쓴 티켓이네요" 거절.

그래서 과거에 연동했던 유저는 **재로그인이 100% 실패**하는 구조였습니다.

해법이 우아해요. 연결 실패 에러 객체의 **userInfo 주머니 안에**, 서버가
"이 계정으로 로그인하려면 **이 새 credential을 쓰세요**"라고 갈아 끼울 티켓을
담아서 보내줍니다:

```swift
let updated = (error as NSError).userInfo[AuthErrorUserInfoUpdatedCredentialKey]
              as? AuthCredential ?? credential   // 없으면 원본으로 폴백
```

**Spring으로 비유하면**: 예외가 단순한 "실패 통보"가 아니라 **복구 재료를 실은
운반체**인 경우예요. `OptimisticLockingFailureException`을 잡아서 최신 엔티티로
재시도하거나, HTTP 409 응답 **본문에** 해결 방법이 들어 있는 API 같은 것.
catch 블록에서 메시지만 읽고 버리면 서버가 건네준 열쇠를 쓰레기통에 버리는 셈입니다.

## 2. 타임아웃은 "양쪽 다" 끝내야 한다 — 한쪽만 포기하면 유령이 남는다

두 번째 원인: 로그인 대기 시간이 **12초**였어요. 처음 연동하는 유저는
"이메일 공유할까요?" 선택, 이름 수정, 암호 입력까지 하니 12초를 쉽게 넘깁니다.

문제는 타임아웃이 터져도 **Apple 로그인 시트는 화면에 그대로** 떠 있었다는 것.
유저가 뒤늦게 인증을 마쳐도 우리 쪽은 이미 "실패"로 끝내버린 뒤라 결과가
조용히 버려졌어요. 유저 눈에는 "다 했는데 왜 안 돼?"가 됩니다.

고친 것 두 가지:
- 대기 시간 12초 → **60초** (실제 사람의 속도에 맞춤)
- 타임아웃이 터지면 `controller.cancel()`로 **시트도 같이 철회** —
  포기할 거면 안쪽(대기 코드)과 바깥쪽(화면) 둘 다 포기시킵니다.

순서도 중요했어요. cancel을 마무리 처리 **이전에** 호출해야 합니다 —
마무리 함수가 컨트롤러 참조를 비워버리니까, 비운 다음엔 철회할 대상이 없거든요.
그리고 cancel이 뒤늦게 "취소됐어요" 콜백을 또 보내는데, 이건 기존의
"이미 끝났으면 무시" 가드가 막아줍니다(같은 결과를 두 번 보고하지 않기).

**Spring으로 비유하면**: `@Transactional(timeout = 12)`이 터졌는데 그 안에서
보낸 외부 HTTP 요청은 취소하지 않아서, 롤백된 주문의 결제가 뒤늦게 승인되는
상황이에요. 타임아웃 처리는 **관련된 진행 중 작업 전부를 한 묶음으로** 끝내야
하고, 뒤늦게 도착하는 응답은 멱등 가드로 무시해야 합니다.

## 3. 에러 분류표에 없는 에러는 전부 "그냥 실패"로 뭉개진다

진단 과정에서 발견한 세 번째 구멍: "이미 쓴 티켓" 거절(missingOrInvalidNonce)이
우리 에러 분류표(AuthErrorMapper)에 **없었어요**. 분류표에 없으면 nil이 되고,
nil이면 화면에는 제일 두루뭉술한 카피 — "잠시 후 다시 시도해 주세요"가 나갑니다.

그래서 유저도, 개발자도, 로그를 봐도 진짜 원인을 알 수 없었던 거예요.
이번에 전용 분류 2종(토큰 소진/네트워크 없음)과 전용 안내 문구를 추가했습니다.

**Spring으로 비유하면**: `@RestControllerAdvice`에 핸들러가 없는 예외는 전부
500 "Internal Server Error"로 뭉개지는 것과 같아요. 에러 매핑이 빈약하면
**정보가 사라지는 게 아니라 숨습니다**. 자주 만나는 실패 모드는 반드시
전용 핸들러 + 전용 메시지를 두세요. 덤: 실패 문구를 보여주는 화면이 **두 곳**
이었는데 한 곳만 고치면 반쪽 수정 — 설계 단계(planner)에서 중복 지점을 미리
찾아내 둘 다 고치게 한 게 주효했습니다.

## 4. "키가 없음"과 "꺼짐"은 다르다 — 기본값의 함정

소리/진동 설정을 저장할 때 흔한 함정이 있어요. iOS의 `bool(forKey:)`는
**키가 아예 없으면 false를 돌려줍니다**. 그대로 쓰면:

> 설정을 한 번도 안 건드린 유저 = 키 없음 = false = **소리가 꺼진 채 시작**

신규 유저 전원의 소리를 꺼버리는 대형 사고죠. 그래서 이렇게 읽습니다:

```swift
defaults.object(forKey: key) as? Bool ?? true   // 키 없음 → 기본 "켬"
```

"값이 없다"와 "false가 저장돼 있다"를 구분하고, 없을 때의 기본값을 **명시**하는 것.

**Spring으로 비유하면**: `@Value("${sound.enabled:true}")`의 `:true`예요.
프로퍼티 부재와 false는 다른 상태입니다. 원시형 `boolean`으로 받으면 이 구분이
증발하니, "안 정했음"이 의미 있는 설정은 `Optional<Boolean>`처럼 다뤄야 해요.
검수(evaluator)도 이 지점을 라이브로 확인했습니다 — 키를 지우고 켜면 "켬",
false를 써넣고 켜면 "끔"이 나오는지 왕복(round-trip) 검증.

## 5. 새 기능은 기존 문의 "노크 규칙"을 재사용한다 — 검증을 두 곳에 만들지 않기

전화가 오면 게임을 자동으로 멈추는 기능. 구현은 사실상 두 줄이었습니다:

```
앱이 비활성화된다는 알림 구독 → presentPauseMenu() 호출
```

"이미 일시정지 중이면?", "게임 중이 아니면(결과 화면 등)?" 같은 분기를
새로 짤 필요가 없었어요 — `presentPauseMenu()` **안에 이미** 그 가드가
있거든요(다이얼로그 없음 + 플레이 중일 때만). 바깥에서 또 검사하면 같은 규칙이
두 곳에 생기고, 나중에 한쪽만 고치는 사고가 납니다.

**Spring으로 비유하면**: 서비스 메서드가 이미 유효성 검증을 갖고 있으면
컨트롤러에서 중복 검증을 안 하는 것. **검증은 문 안쪽 한 곳에** 두고, 새 호출자는
그냥 노크만 하면 됩니다. 덤으로 구독에는 해제가 따라야 해요 — 씬이 떠날 때
`removeObserver` 쌍을 맞추는 것(`@PreDestroy`에서 리스너 정리하는 습관과 동일).

## 6. "강제 스위치로 봤다"와 "진짜 경로로 봤다"는 증빙의 급이 다르다

첫 판 온보딩 힌트는 "한 번 보여주면 끝"이라 테스트가 까다로워요. 구현자는
디버그 강제 스위치(`GANHO_FORCE_CONTROLS_HINT`)로 화면을 띄워 확인했는데,
검수자는 한 발 더 나갔습니다 — **앱을 지웠다 새로 설치**해서, 강제 스위치 없이
"진짜 신규 유저 경로"로 힌트가 뜨고, 뜨는 즉시 플래그가 저장돼 두 번째 판부터
안 뜨는 것까지 확인했어요.

**Spring으로 비유하면**: 테스트 프로파일에서 `@MockBean`으로 통과시킨 것과,
스테이징에서 실제 회원가입 플로우를 돌려본 것의 차이예요. 강제 스위치 검증은
"화면이 그려진다"만 증명하고, 실 경로 검증은 **조건 판정 로직까지** 증명합니다.
중요한 1회성 동작(온보딩·마이그레이션)은 가능하면 실 경로로 한 번은 태워보세요.
