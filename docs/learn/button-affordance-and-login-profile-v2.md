# 버튼 어포던스 + 로그인·프로필 v2 톤 통일

## 한 줄로

**"흰색이라서 버튼처럼 안 보인 게 아니라, 그림자·테두리가 없어서 평평했던 것"** 이다. 흰 버튼에 **입체 그림자 + 또렷한 코랄 테두리 + 살짝 불투명**을 입혀 "이건 누르는 것"이라고 손가락한테 알려줬고, 로그인 창의 어두운 골드 테마를 게임의 밝은 코랄 톤으로 맞춰 화면 전체를 한 가족으로 만들었다.

## 무슨 문제를 풀었나

사용자가 두 가지를 지적했어.

1. 로그인 창이랑 캐릭터 선택창 프로필이 **조잡하다**(대충 만든 느낌).
2. **흰 바탕에 글자만 있는 버튼**이 버튼인지 글자인지 헷갈린다.

코드를 열어보니 원인이 분명했어.

- 게임의 대부분은 이미 **따뜻한 코랄(주황빛 빨강)·네이비 톤**(v2 디자인)을 쓰는데, **로그인 창만 혼자 어두운 남색 + 금색** 옛날 테마였어. 혼자 다른 옷을 입고 있으니 "조잡"해 보인 거지.
- 버튼 중에 `GlassPillNode`라는 게 있는데, 반투명 흰색 알약에 **그림자도 없고 테두리도 흐릿**했어. 그러니 그냥 흰 종이에 글씨 쓴 것처럼 평평했지.

## 핵심 개념 — "어포던스(affordance)"

어려운 단어지만 뜻은 쉬워. **"이건 이렇게 쓰는 거야"를 생김새만으로 알려주는 힘**이야.

- 문 손잡이가 **튀어나와 있으면** → "잡고 당겨"
- 버튼이 **튀어나와 보이면** → "눌러"

엘리베이터 버튼을 생각해봐. 진짜 엘리베이터 버튼은 살짝 튀어나와 있고 테두리가 있어서 멀리서도 "아, 저거 누르는 거구나" 싶잖아. 그런데 벽에 그냥 "3층"이라고 **글씨만 써놓으면** 그게 버튼인지 안내문인지 모르겠지. 우리 흰 버튼이 딱 그 "글씨만 써놓은 상태"였어.

그래서 한 게:

| 추가한 것 | 효과 (현실 비유) |
|---|---|
| **입체 그림자** (아래로 4px) | 버튼이 종이 위에 살짝 떠 있는 느낌 → "튀어나옴" |
| **코랄 2px 테두리** | 버튼의 경계가 또렷 → "여기까지가 버튼" |
| **불투명도 ↑** (0.55 → 0.82) | 배경이 비치지 않아 또렷 → "진짜 물체" |

흰색은 그대로 뒀어. **흰색이 문제가 아니었으니까.** 입체감만 더해줬을 뿐인데 버튼처럼 보이게 됐어.

## 버튼 3계층 — 신호등처럼 중요도를 색으로

버튼이라고 다 똑같이 생기면 안 돼. "제일 중요한 버튼"과 "그냥 보조 버튼"이 구분돼야 눈이 안 헷갈려. 그래서 3단계로 나눴어.

| 계층 | 생김새 | 언제 | 비유 |
|---|---|---|---|
| **Primary** (주연) | **꽉 찬 코랄** + 흰 글자 + 그림자 | "시작", "Apple로 시작" | 무대 한가운데 주인공 |
| **Secondary** (조연) | 흰 바탕 + **코랄 테두리** + 그림자 + 네이비 글자 | "게스트", "뒤로", "취소" | 주인공 옆 조연 |
| **Destructive** (위험) | **딥코랄(진한 빨강)** + 흰 글자 | "계정 삭제" | 빨간 경고등 |

이러면 화면을 딱 봤을 때 "꽉 찬 코랄이 제일 중요한 버튼이구나", "진한 빨강은 위험한 거구나"가 색만으로 전달돼. 계정 삭제 같은 위험한 버튼은 일부러 다르게 칠해서 실수로 안 누르게 한 거야.

## Spring 출신을 위한 비유

- **`ColorTokens.swift`** = `application.yml`의 색 설정 모음. `ganhoCoralPrimary = #FF6B5B` 같은 색을 한 곳에 정의해두고 온 화면이 갖다 쓴다. 색을 바꾸고 싶으면 여기 한 줄만 고치면 전부 바뀜(= 설정 중앙화).
- **`GameConfig.swift`** = 숫자 설정 모음(`application.yml`의 숫자판). 그림자 위치(-4), 테두리 두께(2), 투명도(0.82) 전부 여기 상수로. **코드 안에 숫자를 직접 쓰지 않는다**(매직 넘버 금지) — Spring에서 `@Value`로 빼는 거랑 똑같은 이유.
- **`OverlayActionButtonNode`의 계산 프로퍼티** = 조건부 빈(bean) 같은 거야:

  ```swift
  private var fillColor: UIColor {
      switch style {
      case .primary:     return .ganhoCoralPrimary   // 주연
      case .secondary:   return .ganhoPaper          // 조연
      case .destructive: return .ganhoCoralShadow    // 위험
      }
  }
  ```

  `@Profile("primary")` / `@Profile("secondary")`처럼, 같은 버튼이 style 값에 따라 다른 색을 돌려주는 거지. 이번엔 **이 switch의 반환값(색)만** 옛 빨강·금색에서 v2 코랄로 바꿨어. 버튼의 구조(틀)는 1도 안 건드리고.

## SpriteKit 한 가지 함정 — 그림자가 블러되면 안 돼

`GlassPillNode`는 유리처럼 **흐릿하게 번지는 블러 효과**(`SKEffectNode`)를 쓰고 있었어. 여기에 그림자를 그냥 넣으면 **그림자까지 같이 흐릿하게 번져서** 입체감이 죽어. 

그래서 계층을 이렇게 짰어:

```
self
├─ shadowShape   (z = -1, 블러 "밖" — 또렷한 그림자)   ← 새로 추가
├─ blurEffect
│    └─ background (블러 "안" — 유리 질감)
└─ textLabel     (z = 1, 또렷한 글자)
```

그림자는 **블러 상자 밖**에 둬야 또렷하게 떠 보여. Spring으로 치면, 로깅 필터(블러) 안에 넣을 빈과 밖에 둘 빈을 구분하는 느낌이야. 어디에 넣느냐가 결과를 바꾼다.

## 가장 중요한 약속 — "건드리지 마라" 영역

이번 작업은 **시각(색·그림자·테두리)만** 바꾼 거지, **동작은 단 한 줄도 안 바꿨어.**

- 버튼 크기·위치 상수 → 그대로
- `contains(_:)`, `action(at:)` (어디를 누르면 무슨 일이 일어나는지) → 그대로
- `init(...)` 시그니처 (버튼 만드는 방법) → 그대로
- 로그인/계정/프로필의 기존 기능(닉네임 수정, Apple 연결, 로그아웃, 계정 삭제 등) → 그대로

왜 이렇게까지 조심했냐면, **"옷만 갈아입히기"** 가 목표였기 때문이야. 만약 버튼의 터치 영역(`contains`)을 실수로 건드리면 "버튼이 예뻐졌는데 안 눌려요" 같은 최악의 버그가 나. 그래서 변경 범위를 **색·그림자·테두리로 못 박았어**(QA가 "터치 회귀 0"을 필수 통과 조건으로 검사함).

## 한 가지 더 — 작업 도중 발견한 것

작업 폴더(working tree)에 **내가 시작하기 전부터 사용자가 만들던 다른 변경들**(`PlayerNode`, `ProfileDetailOverlayNode` 등)이 섞여 있었어. 그래서 "내가 바꾼 것"과 "원래 있던 것"을 git으로 구분해서, **내 작업분(시각)만** 평가하고 나머지는 그대로 보존했어. Spring 협업에서 남의 미커밋 브랜치 변경을 덮어쓰지 않게 조심하는 거랑 같아.

## 검증 — 어떻게 "잘 됐는지" 알 수 있나

1. **빌드 성공**: `xcodebuild ... build` → `** BUILD SUCCEEDED **` (묶음 A·B 다 합친 최종 빌드까지 통과)
2. **QA 채점**: 묶음 A 9.0/10, 묶음 B 9.0/10 — 둘 다 "터치 회귀 0", "흰 버튼도 버튼처럼 보임" 필수 관문 통과
3. **눈으로 확인**: 시뮬레이터에서 `⌘R` → 시작 → 로그인 창 → 캐릭터 선택 → 프로필 순서로 봐야 진짜 진실(아래 "안 한 것" 참고)

## 이번에 안 한 것

- **시뮬레이터 실제 화면 캡처**: 로그인 창·프로필은 게임 안에서 버튼을 눌러 들어가야 나오는 화면이라, 자동으로 캡처하기 어려워서 **사용자가 직접 `⌘R`로 확인**하는 게 정확해. (빌드는 통과 = 코드는 안전, 하지만 "예뻐 보이는지"는 사람 눈이 진실)
- **인게임 화면**: 이번 범위 밖(픽셀 톤은 그대로).
